## Description
**Epic — no code lives here directly.** `transformer.rs` is **2,463 lines** and
mixes several unrelated concerns in one file: the model struct + init, the forward
pass, the backward pass, (de)serialization, the Adam optimizer, and the GPU→CPU
weight readback. That is an **R20 (cohesive modules)** violation the Auditor sweep
under-flagged (it filed the symptom as R19 comment banners in ISSUE-0071, and the
type-rename in ISSUE-0061, but not the split itself). This epic does the split
**logically — grouped by concern, not by line count**.

### Target layout
```
training/
  transformer/
    mod.rs            Model struct + init + StepDims + train_step/_masked
                      orchestrator + save/load wrappers; module doc
    forward.rs        embed/attn/ffn forward stage helpers, project_logits,
                      compute_loss
    backward.rs       backward_unembed, ffn/attn backward, clip_gradients,
                      accumulate_embedding_grad
    serialization.rs  write_*/read_* + write_model/read_model + to_bytes/
                      from_bytes/to_layer_rows/from_layer_rows + header parse
  optimizer.rs        grad_buffers, gpu_clip_gradients, gpu_adam_update, Adam
                      consts + MAX_GRAD_NORM  (operate on GpuWorkspace)
  sync.rs             sync_weights_from_gpu  (GpuWorkspace → CPU readback)
```

### The design decision (why forward/backward live under transformer/ but
### optimizer/sync do not)
`forward` / `backward` / `serialization` are **intrinsic to the model** — they read
its fields and its cache layout — so they belong under `transformer/`. But
`gpu_adam_update` and `sync_weights_from_gpu` operate on the **`GpuWorkspace`**, not
the model; they are training-loop machinery. Nesting them inside `transformer/`
would repeat the same category error that made the monolith confusing, so they sit
one level up as `training::optimizer` / `training::sync`.

### The one cross-cutting concern every child shares: visibility
The forward/backward stage helpers are currently **private methods** on
`impl Transformer`. Once they move to sibling files, the `train_step_masked`
orchestrator in `mod.rs` must still call them across module boundaries — so each
moved helper becomes `pub(super)` (visible to the parent `transformer` module),
**not** `pub`. Do not widen visibility further than the call sites require; the
helpers stay internal to the `transformer` module.

### Sequencing against the rename epic
This split rewrites the same lines the **llm rename epic (EPIC-0060,
`Transformer → Model`)** touches, so it is `blocked-by: [EPIC-0060]` at the first
child (0078) — renames land first, then the split moves `Model` (not
`Transformer`). Children below name the type as it exists *after* 0060 (`Model`);
if 0060 has not landed when a child is picked up, use whatever the type is called
at that point and note it.

### Non-goals
- No behaviour change. This is a pure move + visibility adjustment; every existing
  GPU test must still pass unchanged (`--test-threads=1`).
- Not re-splitting attention vs. feed-forward into separate files — `forward.rs`
  and `backward.rs` each hold the whole pass. Revisit only if they themselves grow
  past R1/R20 later.
- Not touching `gpu_workspace.rs`, `device_buffer.rs`, or `embed.rs`.

### Definition of done (what closes THIS issue)
1. All children 0078–0083 are `done`.
2. `transformer.rs` no longer exists as a monolith; the layout above is in place,
   each file is one concern, and no file re-mixes them.
3. `cargo build` + `cargo clippy` clean (zero warnings, R7); the full GPU suite
   (`transformer::tests`, `train_test.rs`) passes `--test-threads=1`.
4. No stuttering module paths introduced (R21): `transformer::Model`,
   `transformer::forward::…`, `optimizer::gpu_adam_update`, `sync::…`.
