## Description

`prepare_wikipedia.py` writes **one article per `.txt`**, named by a fresh
`uuid4()`, with `--limit` defaulting to 2000. That is why `data/input/Wikipedia`
is 2001 files and 14 MB against FineWeb's 1.5 GB. Full English Wikipedia is
~6.9M articles; one file each is a directory no filesystem should be asked to
hold, and `sources.collect()` sorts the whole glob on every pack.

The uuid naming makes it worse in a way that is easy to miss: `sources.collect`
caps a dataset by taking the first N of the *sorted* file list, and its docstring
promises that "the same request must select the same text every time". With uuid
filenames, a re-fetch reshuffles which articles sort first, so a capped
Wikipedia selection silently trains on different text than the run it is meant
to reproduce.

**Wanted.** The `prepare_fineweb.py` shape, on the helper from TODO-0111: a
`--mb` byte budget rather than an article `--limit`, many articles batched per
output `.txt`, deterministic sequential filenames (`wikipedia000000.txt`), and
shards fetched lazily so a small run does not pull all 41.

Target ~20 GB for the full English dump — that is the anchor source for the next
model — but the budget is a flag, so a smaller run stays one command away.

**Keep what is already right.** The Wikimedia dump's `text` is pre-cleaned
prose, so no further cleaning is needed. `--min-chars 500` drops stubs and
should stay. The title is prefixed as a heading line and is worth keeping — it
is the only structural signal in the document.

**Marker neutralization now matters.** The current script writes article text
through untouched. At 2000 hand-limited articles that was survivable; across
6.9M articles the encyclopedia certainly contains an article quoting
`<|endoftext|>` verbatim, which would inject a false document boundary
mid-article. Use the helper's neutralization.

`--limit` can stay as a secondary cap for quick test fetches, but `--mb` is the
control that matters and should be the documented default path. Update the
module docstring — it currently teaches the one-article-per-file model as
intentional, contrasting it with `prepare_fineweb.py`, and that reasoning no
longer holds.

## Definition of done

- A `--mb N` run writes ~N MB across sequentially-named shard files.
- Filenames are deterministic — the same request selects the same text twice.
- Marker-looking text in article bodies cannot inject a document boundary.
- The docstring describes the sharded model, not the per-article one.

### Builder · 2026-08-10
Rewritten onto the shared helper: `--mb` budget instead of `--limit`, sequential `wikipedia000000.txt` names, lazy per-shard fetch, marker neutralization, `--min-chars 500` kept, title still prefixed as a heading. Default is 20 GB — the full English dump.

The filed reproducibility bug is fixed: deterministic names mean a capped selection now really does select the same text twice. Verified with a real 3 MB fetch (92 documents, 11 files) and a dry-run at 20 GB.
