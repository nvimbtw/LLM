## Description

`src/crypto/` (116 lines across `password.rs`, `jwt.rs`, `token_cipher.rs`) is
already a self-contained module with no DB or HTTP awareness — that property is
stated as a layering rule in `backend/CLAUDE.md` and the module honours it. It
is a crate that has simply never been declared as one.

Move to `crates/crypto`, taking `argon2`, `jsonwebtoken`, `aes-gcm`, `sha2` and
`base64` out of `backend/Cargo.toml` and into the new crate's manifest (check
each: whatever `backend` still uses directly stays in both).

Consumers to rewrite from `crate::crypto::` to `crypto::`: `db/mod.rs` (the
create-admin path, which hashes with `crypto::password`), `extractors.rs`,
`ws.rs`, and the auth routes.

This must land before TODO-0098, because `db` depends on `crypto` and a crate
cannot depend on a module of the binary that depends on it.

## Definition of done

- `crates/crypto/` exists; `backend/src/crypto/` is gone and `mod crypto;` is
  removed from `main.rs`.
- `grep -rn "crate::crypto" backend/src backend/crates` returns nothing.
- The crypto crate's `Cargo.toml` names only the crypto dependencies — no
  `sqlx`, no `actix-web`.
- `cargo build` and `cargo clippy --all-targets` clean; `cargo test` passes.

## Comments

### Builder · 2026-07-29

**This artifact's premise was wrong and the shape changed. `crypto` was not a
leaf.**

`crypto/jwt.rs:5` imported `crate::db::user::AccessLevel` (its `Claims` carry an
access level), while `db/mod.rs:12` imports `crypto::password` for the
create-admin hash. As modules of one binary that was legal; as crates it is
`crypto → db → crypto`, which Rust will not compile. The description above, and
`backend/CLAUDE.md`'s claim that this module has "no DB or HTTP awareness", were
both describing an intent the code had already drifted from — a latent R12
layering violation that only became fatal at a crate boundary.

Resolved by moving `jwt` out rather than by moving `AccessLevel` down:

- `crates/crypto` = `password` + `token_cipher`. Genuinely dependency-free of
  this workspace (argon2, aes-gcm, sha2, base64 only), so everything can depend
  on it. This makes CLAUDE.md's stated rule true for the first time.
- `jwt` is now `src/jwt.rs`, a **temporary** module of the binary, folded into
  the web crate by TODO-0103 (amended to say so). Every consumer of `jwt::` is
  already destined for `web`: `extractors.rs`, `ws.rs`, `routes/auth.rs`,
  `routes/user.rs`. Nothing below the HTTP layer issues or verifies a token.
- `AccessLevel` stays in `db::user`, where its `sqlx::Type` derive and the
  Postgres `access_level` enum mapping belong.

Rejected alternatives, for the record:

- *Move `AccessLevel` into `crypto`* — its `sqlx::Type` derive would drag `sqlx`
  into the crypto crate, destroying the very property that makes it a safe
  leaf. The derive must sit on the definition, so `db` cannot supply the
  mapping separately without a newtype, and the orphan rule blocks implementing
  `sqlx::Type` for a foreign type anyway.
- *A shared `domain`/`types` crate for `AccessLevel`* — one 4-line enum does not
  justify a crate, and a crate named for no concern is the grab-bag R20 forbids.
- *Make `Claims.access_level` a `String`* — breaks the cycle by discarding the
  type safety at exactly the boundary where authorization is decided.

The intermediate state leaves one file loose in `src/` for the next six
children, which is against the spirit of EPIC-0094. It is the price of keeping
every step compilable: `web` does not exist until TODO-0103.

`cargo clippy -p crypto --all-targets` clean. 56 backend tests pass. No
`crate::crypto` references remain.
