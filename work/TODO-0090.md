## Description

Today the learning rate ramps linearly over the first `WARMUP_STEPS` (100)
optimizer steps and then stays **flat** at the configured `lr` for the entire
rest of the run. `step_optimizer` (`train.rs:405-421`) computes
`warm = (adam_step / WARMUP_STEPS).min(1.0)` and passes `lr * warm` to
`gpu_adam_update` — there is no decay term anywhere. The classic GPT schedule is
linear warmup **then cosine decay** down to a small floor; the decay is what lets
the loss settle instead of bouncing around the target LR late in training.

### Shape of the fix (train.rs only — does not touch the optimizer/kernel)

1. Add a helper, e.g. `fn lr_at_step(base_lr: f32, step: i32, total_steps: i32) -> f32`,
   that reproduces the current warmup for `step <= WARMUP_STEPS` and then cosine-
   decays from `base_lr` to `MIN_LR_RATIO * base_lr` over the remaining
   `total_steps - WARMUP_STEPS` steps:
   `min_lr + 0.5 * (base_lr - min_lr) * (1 + cos(pi * progress))`, where
   `progress = (step - WARMUP_STEPS) / (total_steps - WARMUP_STEPS)` clamped to
   `[0, 1]`. Add a `MIN_LR_RATIO: f32 = 0.1` const next to `WARMUP_STEPS`
   (0.1 is the common GPT default; keep it a named const so it's tunable).
2. Thread the **total planned optimizer-step count** down to `step_optimizer`.
   `run_training_loop` already knows `total_chunks` and `epochs`; the optimizer
   steps once per `ACCUM_STEPS` chunks plus once at each epoch's tail, i.e.
   `ceil(total_chunks / ACCUM_STEPS)` steps per epoch × `epochs`. Compute this in
   `run_training_loop`, pass it into `train_epoch`, and on into `step_optimizer`
   (both already carry an `#[allow(clippy::too_many_arguments)]`, so adding one
   positional param follows the existing pattern).
3. In `step_optimizer`, replace the `warm`/`lr * warm` lines with
   `lr_at_step(lr, *adam_step, total_steps)`.

### Edge cases to keep correct

- `total_steps <= WARMUP_STEPS` (very short runs, e.g. tiny SFT): guard the
  denominator so it can't divide by zero or go negative — clamp `progress` to
  `[0, 1]` so a short run just stays in/at warmup rather than producing a
  negative or NaN LR.
- The existing warmup comment block (`train.rs:23-33`, incl. the SFT note) should
  be updated so it describes warmup **+ cosine decay**, not warmup alone.

### Definition of done

- `cargo build` / `cargo clippy` clean for the `llm` crate.
- The effective LR is `~0` at step 0, rises to `lr` at `WARMUP_STEPS`, and decays
  smoothly toward `MIN_LR_RATIO * lr` by the final optimizer step (verifiable by
  a small unit test on `lr_at_step`, or by reasoning through the three anchor
  points if a GPU/CUDA build isn't available in the check environment).
- No change to optimizer or kernel code — this artifact is the LR schedule only.

## Comments
### Builder · 2026-07-18
Implemented warmup + cosine decay entirely in `train.rs`, no optimizer/kernel changes:

- Added `MIN_LR_RATIO: f32 = 0.1` next to `WARMUP_STEPS`, and rewrote the warmup
  comment block to describe warmup **+ cosine decay** (incl. the SFT short-run note).
- New pure helper `lr_at_step(base_lr, step, total_steps)` (train.rs): linear
  warmup for `step <= WARMUP_STEPS` (returns exactly `base_lr` at the boundary),
  then `min_lr + 0.5*(base_lr-min_lr)*(1+cos(pi*progress))` decaying to
  `MIN_LR_RATIO*base_lr` at the final step. `progress` is clamped to `[0,1]` and
  the denominator floored at 1, so a run with `total_steps <= WARMUP_STEPS` (tiny
  SFT) can't divide by zero or emit a negative/NaN lr — it just pins to the floor
  past warmup.
- Threaded `total_opt_steps` from `run_training_loop` → `train_epoch` →
  `step_optimizer`. Budget computed as `total_chunks.div_ceil(ACCUM_STEPS) * epochs`
  (the step fires once per ACCUM_STEPS chunks plus once at each epoch tail).
- `step_optimizer` now calls `lr_at_step(lr, *adam_step, total_opt_steps)` in place
  of the old flat `lr * warm`.

Added `#[cfg(test)] mod tests` with two pure-arithmetic unit tests: one pinning the
warmup/decay anchor points + monotonic non-increasing decay, one asserting a
run shorter than warmup stays finite and non-negative.
