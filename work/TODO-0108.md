## Description

With the layout (TODO-0106) and keyed builds (ISSUE-0107) in place, the run
config has to be able to *ask* for a set. `SftConfig` currently has no data
field at all beyond `strip_thinking`, and `orchestrate/sft.py:68` calls
`sft_corpus.build(tokenizer, reasoning)` with no selection, so every fine-tune
trains on every conversation on disk.

**Wanted.** `SftConfig.datasets: list[DatasetSelection]`, defaulting to empty
(= all sets), reusing the existing `DatasetSelection` model and the
`_as_selections` before-validator so `["smoltalk2-think"]` and
`[{"name": "smoltalk2-think", "count": 20}]` are the same request — identical to
`TrainConfig.datasets`. Thread it into the `build()` call and into the keyed
reuse check.

**Explicitly not a curriculum.** `TrainConfig` has `curriculum` for ordered
stages; `SftConfig` must not grow one. The intent is two *separate* runs from
the same base model — a no-thinking fine-tune and a thinking fine-tune —
producing two independently loadable models that can be compared against each
other. Stages would produce one model and defeat the purpose.

**Watch the interaction with `strip_thinking`.** Once sets are selectable, a
thinking set selected with `strip_thinking: true` is almost certainly a mistake
rather than an intent, but it is still a legitimate request (it is how you'd
build a strip-thinking control against the same conversations). Leave both
levers independent; do not couple the flag to the set name.

The `dataset` field of the run's result (`orchestrate/sft.py:138`) should record
which sets were selected, so `meta.json` says what the model was actually
trained on. That is the thing that makes two saved models tellable apart later.

## Definition of done

- `POST /sft` with `datasets: ["<set>"]` fine-tunes on that set alone.
- Omitting `datasets` keeps today's behaviour: every set on disk.
- The selection reaches the ISSUE-0107 key, so two runs on different sets do not
  share a built dataset.
- `meta.json` records the selection for the finished model.
