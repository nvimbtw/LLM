## Description

`data/sft/` holds 19 loose files — `smoltalk-000.jsonl` … `smoltalk-018.jsonl`,
777 MB — written by `scripts/prepare_smoltalk.py` against the old flat layout.
TODO-0106 keeps them working by collecting loose root files as a set named
`root`, but leaving them there is a trap: `root` is a fallback, not a name
anyone would knowingly select, and a run that means "everything" would silently
mix this legacy set into any future selection.

**Wanted.** Move them into a named set folder — `data/sft/smoltalk/` — so they
are selectable by a name that says what they are, and `root` goes back to being
an empty fallback.

**Shape of the fix.** A small idempotent migration script under `scripts/`
that moves loose `.jsonl` from the SFT root into a named folder, defaulting to
the set name `smoltalk`, and does nothing on a second run. Follow
`scripts/migrate_sft_bare_tags.py`, which already exists for a previous SFT
data migration — same register, same directory.

Two things to get right:

- **Move, don't copy.** 777 MB duplicated for no reason, and a half-migrated
  state where a file exists in both places would be collected twice — the same
  conversations trained on twice with no indication.
- **Don't clobber.** If the destination folder already holds a file of that
  name, stop rather than overwrite; the source of truth for these is a re-run of
  `prepare_smoltalk.py`, but only if it is actually still reproducible.

`prepare_smoltalk.py` itself writes to the flat root and will keep recreating
the problem. Point its output at the named set folder as part of this change —
it is a one-line change to where `clear_previous` and the writer look, and
leaving it stale means the next fetch undoes the migration.

## Definition of done

- `data/sft/smoltalk/` holds the 19 files; `data/sft/` has no loose `.jsonl`.
- Re-running the migration is a no-op.
- `prepare_smoltalk.py` writes into the named set folder, and its
  `clear_previous` is scoped to that folder.
