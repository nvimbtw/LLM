## Description

Eleven files totalling 9,495 lines sit loose in `backend/src/` alongside
`main.rs`, and the three "crates" the project talks about (`routes`, `db`,
`crypto`) are not crates at all — they are modules of the binary. The only real
crates are `llm` and `tokenize`, and they live *inside* `backend/src/`, which is
where a package's own source goes, not its dependencies'.

`backend/CLAUDE.md` documents a structure that does not exist. It states that
`crates/*` are "Cargo workspace members declared in `backend/Cargo.toml`" and
names `crawler`, `data_pipeline`, `tokenization`, `llm`. There is no `crates/`
directory, there is no `[workspace]` section, and none of those four names
match what is on disk. Anyone following the file is reading fiction.

The goal is one invariant: **every source file belongs to a crate whose purpose
is one sentence, and the dependency graph between them is acyclic and
one-directional.** That is R20 (cohesive modules and honest crate boundaries)
applied at the package level rather than the module level.

### Target

```
backend/
├── Cargo.toml        [workspace] root + thin bin package
├── src/main.rs       entrypoint only
└── crates/
    ├── storage/      data/ layout · no deps                101
    ├── crypto/       argon2 · JWT · AES                    116
    ├── tokenize/     moved from src/tokenize
    ├── llm/          moved from src/llm       → tokenize
    ├── db/           sqlx + migrations        → crypto     2050
    ├── training/     datasets + train entry points         2928
    ├── synth/        synthetic generation                  2274
    ├── labeling/     autolabel + gather                    1123
    ├── jobs/         queue + train_worker + cycle          2848
    └── web/          routes + extractors + ws              3909
```

Dependency order, strictly acyclic:
`storage`/`crypto`/`tokenize` → `llm` → `training`/`synth`/`labeling` → `db` →
`jobs` → `web` → bin.

### Groupings that are not one-file-per-crate, and why

- **`jobs` = queue + train_worker + cycle.** `train_worker` imports
  `crate::queue::{ProgressTick, emit, frame, lock}` and `queue` calls
  `train_worker::{run, snapshot_frame, Outcome}` — a genuine cycle. Rust forbids
  circular crate dependencies, so these cannot be separated without first
  extracting the shared progress types. Not worth doing as part of a move.
- **`labeling` = autolabel + gather.** Both generate replies destined for
  `raw/preference/`; they differ only in who judges (a rule-based
  `llm::autolabel::Judge` vs a person). Same concern, two strategies.
- **`web` = routes + extractors + ws.** `extractors.rs` is the actix auth
  extractor and `ws.rs` is socket auth; both are pure web glue with no meaning
  outside the HTTP layer.

### Scope boundary

Files move **as-is**. `training.rs` (2,928 lines) and `synth.rs` (2,274) are
well past a reviewable size, but splitting them into modules is deliberately
*not* part of this epic — keeping the diff mechanical is what makes it
verifiable. File splits get their own artifacts afterwards.

### Traps, called out per child

1. `sqlx::migrate!("./src/db/migrations")` (`db/mod.rs:21`) resolves against
   `CARGO_MANIFEST_DIR`. Moving `db` into a crate changes that base silently,
   and the failure is at **runtime on startup**, not at compile time.
2. `sqlx::query!` verifies against a live database at compile time, from
   whichever crate holds the macros. `backend/.env` currently covers everything.
3. Moving a module into a crate promotes its `pub(crate)` surface to `pub`.
   Keep the surface deliberate rather than blanket-`pub`ing to make it compile.

### Interaction with open work

ISSUE-0065 (`db::user::User` → `UserRow`) and ISSUE-0068 (`db::model::Model` →
`ModelRow`) both target `db/`, which TODO-0098 relocates. They do not conflict,
but whichever lands second needs its `location` rebased onto `crates/db/`.
ISSUE-0017 (missing doc comments, R9) grows in scope as `pub(crate)` items
become `pub`.

## Definition of done

- Every child `done`.
- `backend/src/` contains `main.rs` and nothing else.
- `cargo build` and `cargo clippy --all-targets` are clean at the workspace
  root; `cargo test` passes for every member.
- `cargo metadata --no-deps` lists all ten crates plus the binary as workspace
  members.
- No crate depends on a crate later in the order above; `cargo build` proves it
  (a cycle simply fails).
- The "Directory structure" section of `backend/CLAUDE.md` matches the tree.
- The app starts and runs migrations against a clean database — the check that
  catches trap 1, which nothing at compile time will.
