E7 — Entity prelexing, priced in tokens

engine/explore/entity · e7_entity_vocab.py · uses the packed 110k corpus + the shared 8k BPE

What was done

A pure token-accounting probe (no model needed). For every Capitalised, name-like phrase in the corpus we compute the number of BPE pieces it costs every time it appears, then simulate giving the top-K phrases single token ids (the E5 "entity prelexing") and tot up the corpus-token savings.

Reading: a single-token budget of 64–512 slots buys a ~4–9% corpus token reduction with no change to the modelling code at all, simply by feeding the tokenizer a tiny static lexicon. The savings-per-mention saturates ~3.7 because the top phrases are exactly the long ones (australia 4 pieces, american_english 6, belgium 3).

Interesting / worrying

  • "australia" costs 4 pieces × 84 mentions = 336 noisy tokens total; one token saves 252 of them. The same pattern holds for the rest of the top list — the current tokenizer leaves a sizable, purely entity-flavoured inefficiency on the table.
  • Savings are sub-linear in budget (2048 slots only ~1.7× the 512-slot gain): coverage of any single corpus is bounded, so the right entity-slot count is easy to tune with this same script at train time.
  • At ~77 mentions per 1000 tokens the corpus has a high entity density — one reason a knowledge-graph idea (E4) is worth pursuing here.

Why it would be a good addition

Three concrete, cheap wins, none touching engine model code:

  • Entity lexicon at tokenizer build time. The BPE can be trained with a fixed list of "don't split" phrases (the tokenizer library supports it in one call). Data/artifacts/tokenizer gains a manifest of the top ~512 entities. No forward-path change — the model simply sees longer, less noisy ids.
  • Per-doc token budget. Entity-dense domains (legal, geo pages) currently blow up context length; a prelexed vocab keeps them in window.
  • Downstream eval sanity. The tokenizer is also what eval uses — "australia" becoming one token instead of four improves any entity-oriented metric without touching the evaluator.

Verdict: a 1-file, non-breaking data-prep change, worth a branch immediately — and it strengthens the knowledge-graph proposal (E4) whichever way the modelling side goes.

How it changes the workflow

  • The tokenizer-training step gains reducer — well, it gains a flag (--entity-lexicon) pointing at e7's list; tokenizer artifacts stay reproducible.
  • Corpus pack can recompute its per-doc token budget with this same script, so savings are documented at train time.
  • Eval/CI gain a cheap "entity token cost" gate with no silent assumptions.
