E1 — RoPE geometry

engine/explore/rope · e1_rope.py · model-free (pure math on the engine's rotation scheme)

What was done

Took the engine's actual RoPE implementation (interleaved adjacent-pair rotation, head-dims 32 channels, no precomputed table) and measured the geometry it imposes on forward positions: how quickly two positions decorrelate and — crucially — where the encoding wraps around and stops being recognisable at all.

engine/.venv/bin/python engine/explore/rope/e1_rope.py > engine/explore/rope/e1_rope.json

Runs in ~2 s on CPU. results.json = e1_rope.json.

Key finding — with the default base of 10k, roughly half of the 32 positional channels have already aliased by the time the model has seen ~128–512 tokens: the rotation has done a full lap in those channels and can no longer tell positions apart. Raising the base delays the decay (positions stay distinguishable further out) but does not remove the wrap: even at base 1M, 63% of channels are aliased or indistinguishable at offsets of hundreds.

Interesting / worrying

  • The similarity curve is not monotonic (dist 32 ≈ 0.60–0.71 sits above dist 16 for several bases); that hump is the wrap boundary where a chunk of channels return to (approx) 0 distance. Fine-grain position is only available in the low-frequency channels.
  • In the trained model the roof is e2: heads typically attend to a broad envelope — see the attention report. RoPE aliasing means "distant token" is effectively system-noise for many channels, so there is little room for a genuine long-range copy head.

Why it would be a good addition

Three engine-friendly proposals, all cheap and orthogonal:

  • Base schedule / bigger default from a config knob. In this corpus the maximum usable distance is ~256 tokens; 10k is a legacy choice. Making rope_base plumbed through TrainConfig (it is currently a private constant) lets users dial range vs. fine-grain without a code change.
  • Two-segment base (NTK-style). Use one base for the first half of the channels (fine local) and a much higher base for the second half (background position). Implemented as a precomputed frequency vector — a ~15-line change, no positions change in the maths.
  • Wrapping guard option. An optional "cap" on rotation so channels never complete a full lap within ctx; trade few channels for well-defined long-range positions.

Verdict: an opt-in config + NTK-style composite base is a 3–8 line footprint in transformer.py with an immediate effect on any long-context task — the engine ships a *clean* base knob, the rest of the codebase is untouched.

How it changes the workflow

Today positional behaviour is invisible; on launch a user can't tell unless their task needs long-range memory. Adding a measured knob means:

  • At the training step: pick a base matched to the corpus window (here, ~1e5–5e5 for windows 128–256, or adaptive composite).
  • At the eval step: a unit-test/probe rope_assert gives a sanity regression: "no channel wrapped before distance D".
  • The experiment is the tool: e1_rope.py becomes a quick report check when anyone touches positional frequency.
