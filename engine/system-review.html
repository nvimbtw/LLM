LLM Engine — Full-System Deep Review

An exhaustive, scored review of the entire LLM stack — Python training/serving engine, Rust backend, Next.js frontend, data scripts — written for one target: an RTX 3060 with 8 GB VRAM.

Scoring rubric: 9–10 = designed like a senior systems engineer · 7–8.9 = solid, small gaps · 5–6.9 = works but has real limits · <5 = needs real work before it's trustworthy.

Stack: Python·PyTorch 2.13 + FastAPI Model: decoder-only GPT (RoPE, Pre-LN, tied emb) Real models: 6.83M params (256d/4h/6L/ctx 512) Corpora: 1.5 GB input + 454k SFT convos Device: RTX 3060 · 8 GB

1 · What this system is

A self-hosted, from-scratch language-model stack. The Python engine (this folder) owns everything that touches a model: training a byte-level BPE, packing corpora, pretraining, SFT, evaluation, and an HTTP/SSE serving API. A Rust backend (backend/crates/) adds users, database, job queue, template + markup port, and supervises the engine process. A Next.js frontend (frontend/) renders chat, training dashboards, and benchmark charts. Data scripts (scripts/) fetch corpora (TinyStories, Wikipedia, FineWeb, SmolTalk) and generate synthetic SFT data via an LLM teacher.

3 · The model itself

Architecture review

7.4
llm/model/transformer.py — decoder-only, 6.83M params in production

What it has

  • RoPE rotary positions, precomputed cos/sin tables (transformer.py:31)
  • Pre-LN blocks, residual stream, final LN
  • Tied embeddings (embedding table transposed as the output projection) — halves the embedding O(V·d)
  • KV cache with correct positional RoPE offsets (transformer.py:66-92)
  • Fused flash attention via scaled_dot_product_attention in bf16
  • No dropout at all (fine for a 6M model on 500M tokens)

What's missing, and what each would buy

  • SwiGLU / GeGLU FFN → ~1-2% loss gain for +0.4x params; cheap win at this scale.
  • No QK-norm or value-norm — many small models degrade less with it. Try it.
  • No RoPE NTK-style scaling — the ROPE_BASE is fixed 10000 and context is hard-baked; you can extend ctx 512 → 2048 on the same card easily.
  • LN has biases + subtracts mean — LayerNorm growth mode is standard, but removing mean-subtract & bias (RMSNorm) is a free norm-stability win at this scale. 25% at most difference.
  • Single-query / grouped-query head — at 6-30M params, MQA/GQA shrinks KV cache, which pays at inference more than at training.

Where the real compute cost goes

8.2

With 6.83M params, a batch=8 × ctx=512 step is ~167 GFLOP — about 13 ms at fp16 on a 3060. The engine is measured at ~30 ms/step with tf32+bf16+compile; the residual is attention + launch overhead. This is textbook-correct for the card: nothing is wasting your VRAM. The one real omission is throughput in production: real runs train at ~6.6 steps/s, not the ~30/s the kernels would allow — see §7.

4 · Tokenizer & vocabulary

Byte-level BPE + fixed special block

9.3

Strengths

  • Wraps HF tokenizers — battle-tested Rust; no reimplementation bugs.
  • Single-file tokenizer.json carries added tokens — a reloaded vocab.json/merges.txt pair would silently split markers; the format choice here prevents a real failure class.
  • Special-token indices are stable by construction: a fixed 64-slot reserved block, append-only policy (special.py:1-4).
  • Corpus-side anywhere only records which marker ids actually appeared; that record drives SFT warm-start (a genuinely subtle cross-stage correctness design).

Weaknesses

  • max_vocab 8192 is small; English words split into many byte merges (~2.1 tokens/word) — hurts both compression and training signal per token.
  • Vocab is retrained per corpus; a corpus change silently renumbers everything — the copy-me-beside-weights only saves the model from tokenizer breaks *after* pack. The boundary between "new vocab" and "same vocab" is only decided at the data dir level.
  • No Unicode normalization / no pretokenizer customization — byte-level is right, but minimizing whitespace-vs-say punctuation variation is not free.
Fix: raise max_vocab to 16384–32768Fix: train vocab per full corpus, then freeze; version it in meta.jsonFix: lower min_frequency to 1 for small corpora, it's the strongest lever on a 6M model

5 · Corpus pipeline

pack.py · plan.py · sources.py — a stand-out subsystem

9.5
Storage: 390M tokens → 747 MB uint16 corpus.bin + segments.json sidecar

Apart from the default-8 batch being small (§7), this is the finest-engineered part of the whole stack. It: streams to disk (2M-token buffers, 18× RAM amplification avoided), keeps a segments.json so per-epoch document shuffling never teaches cross-doc boundaries, uses a deterministic (name,count) cap for reproducibility, builds batches as one contiguous slice (no per-row gathers, las vectorize the numpy copy), and drops partial batches instead of padding (plan.py:125-128). The memory notes (stream_length 745 MiB copy saved, frequent_tokens blocking to avoid 13 GiB tolist) show real production care.

The only real limits: no dedup across datasets (FineWeb+TinyStories may overlap), and the SFT corpus (777 MB, 454k conversations) is not yet linked to its sources or filtered reproducibly.

6 · Training loop

loop.py · plan schedule · optimizer

8.8

Strengths

  • fused AdamW (one kernel per step vs per-tensor), cosine decay to 10% floor + warmup.
  • bf16 autocast with master fp32 weights; no GradScaler needed (bf16 keeps fp32's exponent range, so no loss scaling to tune — loop.py:35)
  • torch.compile on the fwd+loss as one graph (the fp32 cross-entropy materialization is fused away: measured 14 of 33 ms)
  • Loss recorded in a device buffer and read back once per report window — no per-step .item() sync.
  • Cooperative cancel at a step boundary, SSE frames every ~150 steps.

Weaknesses that cost real epochs in a long run

  • No gradient accumulation — to grow the effective batch (bs 8 is tiny) you must raise batch_size and VRAM/h2d at once.
  • No EMA window — a deterministic EMA of weights is free and helps small models on hard data.
  • No best-epoch tracking — checkpoints overwrite; the "best" check for eval is manual.
  • No resume — a 12k-step run interrupted costs everything (both real model dirs are 'cancelled').
  • lr schedule is global across curriculum stages (fine) but no stage-decay knob.
Fix: grad-accumulate a fixed number of micro-batches to hit 32-64Fix: save best-by-EMA + last epochs, and expose --resume from a checkpointFix: add a scheduler curve test under bench parity

7 · Efficiency on the RTX 3060 — the gap

Bench harness says ~33 ms/step; real runs live at ~150 ms/step

6.2

Real meta.json records: 12,600 steps in 1,908 s = 6.6 steps/s ≈ 151 ms/step, and 5,781 steps in 1,023.5 s ≈ 177 ms/step. bench.py micro/full predicts ~33 ms/step at the same config. That ~4.5-5.5× difference is the single biggest efficiency mystery to profile first. Likely suspects:

  • report/epoch work: epoch_stream rebuilds the whole stream each epoch (a full-memory copy), checkpoint saves per epoch, SSE + sleep(2ms) per report — none should cost 120 ms/step by itself
  • H2D copies with non_blocking=True on pageable numpy arrays — pinned copies would allow true overlap.
  • Diagnostics every few reports (explicit softmax + SVD + histograms) — could be a large fraction of a real run.
  • Compile warm-up, allocator growth, cudnn autotune on the first epochs.
  • GPU shared with the rest of the machine (frontend/dev server, compositor) on a 3060.
Action: time bench micro vs real-run step — the harness already splits per-phase timing, so the delta names itself Action: pin host buffers (allocate stream via .pin_memory()) Action: keep diagnostics cheap at real scale

VRAM budget: the 6.8M model trains at ~0.8-1.2 GB peak; the "balanced" 30M preset at batch 8 lives in ~2.5 GB. Even a 120-150M-param model (768d/20L+) stays under ~4-5 GB including Adam. The 3060 is *not* your constraint — the token volume and step-utilization are. Prefer batch 16-32 + BF16 + compile over a smaller model before you consider anything else.

8 · SFT + chat template

One template for train & prompt; mask is derived from the scaffold

9.2
  • build_training_example renders the exact marker scaffold the runtime serves — template drift is structurally impossible (chat/template.py:226).
  • Loss masking includes the closing <|/assistant|>, marks the last position 0, and averages over named tokens only (loop.py:394).
  • Warm-start of marker embeddings whose ids the base model never saw — informed by special_ids_seen, a genuinely cross-run correct idea.
  • 454k SmolTalk conversations + synthetic teacher-generated data (scripts/generate_sft_llm.py with real gold examples).
  • Grounding: the base-model tokenizer travels with the fine-tune, so a later pretrain cannot silently renumber tokens under it.

Improvements: add SFT ↔ source dedupe; replay thin prose from the base model's pretrain corpus into SFT windows (the frontend TS already defines replay_tokens — the engine doesn't do it); seed some system-prompt scaffolds into the pretrain corpus, since system blocks are trained today but never exercised at sampling.

9 · Decoding & sampling

sample.pick() — solid core, missing the one lever that matters most for this size

6.4

Works well

  • temperature collapse → argmax; top_k / top_p self-disable at neutral values
  • sampler runs on an explicitly f32 logit clone, so masking never corrupts the model's own logits
  • decode stops on <|endoftext|> in infer and <|/assistant|> in chat
  • grammar masking (markup.py) costs microseconds per step — few dozen ids masked

Gaps

  • No repetition penalty (the #1 text-quality lever at 6M-120M params; the eval scorecard literally gates on a repetition metric, so the pain is measured, not hypothetical)
  • No min-p / typical sampling (cheap, big quality win at small-model scale)
  • No frequency/presence penalties (a useful interactive knob for chat)
  • The loop only stops at end-of-text / token cap; no explicit stop-on-repetition (loops burn the whole budget).
Fix: add repetition_penalty ≤ 1.2 to sample.pick (both chat and eval paths) Fix: add min-p = 0.02-0.05 for the eval suite Fix: stop-token + repetition cut-off in decode loops

Markup grammar at decode

9.8

OpenBlocks tracks block state and masks illegal markers: closes what's open before the turn ends, refuses needless depth past 6, forbids other-role scaffold and reply-id tokens, enforces list→item nesting and only-child rules, and on token-cap drain produces well-formed closers (chat/markup.py:1-6). This is better *structural* decoding than most production chat systems run. The one rule-set addition that would extend it: budget-aware thinking (<|think:low|> ⇒ cap thinking block) — score for that lives in the thinking section.

10 · Thinking blocks & budgets

The reservation is excellent; the policy is one flag

6.0

Design is right: three budget markers condition training, as one-token embeddings, not labels; the training mask deliberately excludes them; a "strip_thinking" flag exists to make the model answer directly on the same data. What's not there is any runtime enforcement. Nothing at generation:

  • caps how many thinking blocks it opens, or how long one runs (a model with a low budget can burn its whole length budget in <|thinking|>)
  • forces a decision between closing the block and ending the turn (a dangling thinking block is well-formed right now)
  • interprets the budget value at all — "low/med/high" maps to nothing

All three are one extension to the open-block machinery (like the markup grammar) plus one token-count cap. For the 3060's 6M-30M models, which gain from showing thinking at all but can't sustain it unaided, budget-regulating decode is a free feature increase that buys the most "intelligence per token" on this machine.

11 · Inference & serving

Runs are arbitrated; inference is not

7.0

Good

  • One Registry, one device line: EngineBusy=409, wait/cancel contracts, SSE with backlog-replay for late subscribers (runs.py:1-9).
  • Cooperative cancel lands on step boundary — weights consistent, always.
  • Single model+tokenizer cached per process; load once per request works for short chat.
  • No base64 blobs: routes are tiny wrappers onto a pipeline.

Gaps

  • Inference and chat are not arbitrated against running runs — a /chat or /infer during a training run shares VRAM and compute with no gate, no queue, no admission control. On an 8 GB card with a 30M model + a 6M run this is fine; with 120M+ it's an OOM & a half-second-per-token regression.
  • One model in memory at a time; switching models evicts the previous (new load per switch).
  • No KV-cache reuse across turns (multi-turn chat re-runs the whole prefix each time).
  • No continuous batching; a single /chat saturates the GPU for its whole turn.
Fix: gate /infer and /chat behind a lightweight device-mutex; queue or 409 Fix: LRU model cache (2-3 slots) instead of evict-everything. Fix: paged KV / "prefix sharing" for 2+ turn conversations (prefill only the delta)

12 · Evaluation

Measured like a scientist, marked down only on coverage

9.0
  • Byte-5-gram baseline with Witten-Bell interpolation — a fair "did it learn beyond a counting table" floor (ngram.py).
  • A bits-per-byte unit that is tokenizer-independent, a logistic mapping with BPB_MID calibrated from real models, and a score_stderr computed per-conversation — all written with statistics in mind.
  • Language / assistant / markup suites kept separate, with weight redistribution when a stage is unavailable — the composite never silently gives zero to a not-yet-ported path.
  • Deterministic eval seed; report JSON stored beside the weights.
  • Gates: the variety/repetition gate keeps the composite honest about loops.

But: the markup pair stage and the language grammar-pair stage are both marked "not ported yet" — the composite evolves by dropping their weights, so today the score is really language + words only… which is reasonable but wasn't the intent. And there is no extrinsic suite — no HellaSwag/PIQA-style 0-shot slice. For a training-run pipeline this is a defensible choice, but three small exact subsets are the cheapest way to know "is my change worth it".

Fix: port the pair stage to restore markup's 0.40 weight Fix: add one HellaSwag-style 0-shot slice (~300 examples, ~3 min of eval) Fix: persist the eval config + timestamp in meta so two runs of the same model are diffable

13 · Diagnostics & observability

Better than most companies ship

9.2
  • Per-report: per-layer grad norms, optimizer update:weight ratios (snapshot-before/after, not derived from Adam math), residual RMS, per-head attention entropy, activation Z-histogram, embedding anisotropy (mean-corrected) + PCA-2/3 projections of frequent tokens.
  • Sampled on ~a handful of steps per run (report every ~150 steps, diag every few reports) so the cost never touches the fast path; the recording path swaps in an explicit softmax only for the measured step — elegant scoping via a context manager.
  • The whole array survives as a JSON frame, and the frontend renders them as charts (embedding globe etc).

Gaps: nothing surfaces throughput/step or GPU utilization; the epoch summary only lives in meta.json. Fix: emit tok/s, VRAM and util in the same progress frame — five lines of code and it answers "is it slow because of me".

14 · Reproducibility, checkpointing, resume

Reproducibility is doc-level good, math-level not

6.4
  • Shuffle is seeded (seed + epoch), pack is deterministic, count-caps are name-sorted, eval seed is fixed → same data order every run.
  • But torch itself is non-deterministic: dtype accumulation, flash-attention kernels, cudnn autotune — and the training loop never sets torch.manual_seed (only bench.py's parity mode seeds by hand).
  • Seeds aren't logged into meta.json, so even repetition-reseeded runs can't be replayed bit-for-bit at eval time.
  • Checkpointing: epoch-per-file to checkpoints/, latest weights at model.pt, no resume. Both real trained models are 'cancelled' — no finished pipeline has ever been produced!

15 · Engineering quality (types, tests, CI, security)

Careful code, fragile tests-column

7.0

Solid

  • Dataclass/Pydantic types everywhere; config == API body; weights_only=True on checkpoint loads; nothing ever evaluates untrusted data.
  • bench.py: micro/full/parity with CUDA-event timing, parity bit-exactness checks — real engineering.
  • Error paths: corner-case validation (dimension % heads, odd head_dim), .partial swap files, runtime guards that turn silent corruption into loud failures, clean per-pipeline error classes mapped to HTTP 4xx.
  • Clean separation layers (config - corpus - model - train - serve).

Weak

  • No pytest at all; harness is the only automated thing and it's not wired into any CI (no .github).
  • Regression risk is concentrated: the batch vectorization, RoPE math, sampling masks — each is hand-verified in comments, not by tests.
  • No typing enforcement: pyrightconfig exists, but nothing runs it; # noqa import comments suggest they'd like it.
  • Some untested frontiers: tolerance flags, curricula (stage/epoch redistribution edge), dynamic vocab swaps.
Fix: add pytest tests for rope parity, mask/target alignment, markup grammar law (open/close), sampler determinism — each ~20 lines Fix: wire bench.py check + parity into a tiny git hook / GH action Fix: run pyright --fatal-warnings in that action

Security

7.0
  • weights_only=True kills the classic pickle RCE from a tampered checkpoint
  • datasets list is read-only; model list only reports meta; tokenizer file checked for existence before load
  • — No auth middleware at all; any local process can POST /train and burn your GPU, or /models to list filenames.
  • — No rate limiting or body-size cap on /chat or /infer (a megabyte prompt floods a small card).
  • — Recent meta shifts (paths via DATA_DIR) are environment injection surface — only from trusted env, fine.

16 · The diploma: "what would I build next on a 3060/8GB"

Phase 1 — free wins (a day)

  • Repetition penalty + min-p in sample.pick (both chat and eval) — the highest per-token quality lever; adds maybe 4 lines.
  • Preserialize + pin_memory tensors in planning; GPU utilization will likely jump when host transfers overlap.
  • Seed training deterministically (torch.manual_seed + manual_seed_all, logged into meta.json), accepting the ~10-15% per-step cost for an exactly-replayable run.
  • Admission control: 409 in /infer and /chat while a run is busy (the Registry already knows).

Phase 2 — quality (a week)

  • SwiGLU + RMSNorm — 2 edits, maybe +0.05 bpb improvement on the same data; refresh the 30M (balanced) run and measure.
  • Gradient accumulation to effective batch 32 — same LR, more gradient signal per step, VRAM flat.
  • Checkpoint resume + best-EMA saving — stops every run ending as "cancelled".
  • Port the markup pair suite so the composite has its real 40% weight back.
  • RoPE-NTK scaling: take a 512-ctx checkpoint to ctx=768; regenerate the bench eval at it.

Phase 3 — product (a month)

  • Budget-governed thinking decode (cap tokens per block by the budget marker).
  • Multi-turn prefix KV reuse; LRU of 1-2 models; batch 2-4 requests with a tiny scheduler.
  • A single ~120M-param model at ctx 1024 over the FineWeb packet — the thing that fits in 8 GB and qualifies as "a real model"; expect ~1.6 bits/byte held-out against the 5-gram baseline's ~2.4.
  • Extrinsic 0-shot suite (HellaSwag slice) top-level in the eval picker.
  • CI: pytest + pyright + bench parity gate.
