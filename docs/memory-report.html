Engine memory: what actually uses the RAM

Measured on this machine, 15 August 2026, against the 4.17 billion-token corpus currently on disk — after the WSL bump to 12 GB RAM / 8 GB swap / 6 cores. Every number below came from running the code, not from reading it.

fixed  All three findings have since been implemented

Diagnostics are unchanged — 32 tracked tokens, PCA rows and per-head entropy all still populate. The reasoning and the measurements behind each change are in ADR 0011; the three "fixes" listed further down are the plan they were built from.

The short version

  • The token path is already solved. Packing streams, the corpus is memory-mapped, an epoch is never materialised, batches are gathered into one reused buffer. Peak memory there does not scale with the corpus, and the measurements confirm it.
  • Two things still scale with the data, and both are outside that path: BPE tokenizer training (measured 3.6 GB on 3.4 GB of text, extrapolating to ~10 GB for Wikipedia alone and ~15 GB for the whole input/ tree) and the diagnostics token histogram, which pulls all 8.3 GB of corpus.bin resident and costs 64 s before the first training step — on every run, even when nobody is reading the diagnostics.
  • Smaller packets do not help either one. For BPE the resident structure is the word→count map, not the text — chunking the input does not shrink it, only sampling does. For the histogram, a strided sample of 1-in-16 gives a byte-identical answer in 2.1 s instead of 64.1 s. Taking the first N tokens instead — the obvious "one packet at a time" reflex — is measurably wrong here.
  • The new WSL config genuinely helps the memory-mapped corpus (there is now room to cache most of it) but it does not rescue an uncapped tokenizer build. The extra cores are free: 6 threads vs 2 was 2.3× faster for 3% more RAM.

1. Where the engine already goes to disk, and at what point

Four mechanisms, all of them deliberate and all of them documented in the source. This is the answer to "at what point do we save to disk":

PointWhereWhat it bounds
Every 2,097,152 tokens, during packing llm/corpus/pack.py — FLUSH_TOKENS = 1 << 21 The buffer is a Python list, where a token costs ~36 B instead of the 2 B it occupies as uint16. Flushing at 2M tokens caps that at ~72 MiB of buffer per 4 MiB write, so packing peak is constant in corpus size. The same flush logic runs in corpus/sft.py, writing corpus and mask in lockstep.
Never read back whole pack.load_corpus, sft.load — np.memmap(..., mode="r") The 8.3 GB corpus.bin is file-backed, not anonymous. Pages are clean, so the kernel reclaims them under pressure instead of the OOM killer taking the process. np.fromfile here would be 8.3 GB of private memory.
Per batch, during training llm/train/plan.py — EpochStream, iter_batches The shuffled epoch exists only as index arrays (57,389 documents × three int64 columns ≈ 1.4 MB). Spans are copied on demand into one pinned buffer of batch × ctx + 1 tokens, reused for the whole run.
Per epoch, after training model/checkpoint.py, storage.py Weights, a copy of tokenizer.json, meta.json. Not a memory mechanism — it is what makes a run resumable and reproducible.

All of it is atomic: corpus, mask and checkpoint go to *.partial and are renamed, so an interrupted or OOM-killed build leaves the previous artifact intact rather than a truncated file that still loads.

Read the last two lines together. Everything the training loop needs fits in 681 MB of host RAM and 383 MB of VRAM. The jump to 8.4 GB is one line: Collector.__init__ calls frequent_tokens(corpus), which makes two full passes over the memory-mapped corpus (flat.max(), then the blocked bincount) to find the 32 most frequent token ids. It pulls all 8.3 GB resident and costs 64 s before step 1 — and my probe passed on_progress=None, so nothing was ever going to read the result.

The memory is clean, file-backed and reclaimable, so this is not itself an OOM. What it is: it evicts everything else from the page cache at the exact moment the run starts, and on the old 8 GB VM it was the difference between "cached" and "every batch hits the disk".

Growth is sublinear — distinct pretokens saturate — but it does not flatten. Fitting the four points and extending them:

  • Wikipedia alone (19 GB, 71,673 files): ~9–10 GB peak. That is inside 12 GB on paper and outside it in practice, once the engine, the backend, the page cache and the dev server are counted.
  • The whole input/ tree (51 GB, ~150k files): ~15–17 GB peak, and around an hour of CPU. It does not fit, at any WSL setting short of a much larger memory=.

This is live, not hypothetical: the Chinchilla 1 preset in presets.json caps FineWeb at 3,531 files and then selects Wikipedia uncapped, with rebuild_dataset: true. The count caps in the config are currently the only thing standing between a run and this ceiling, and they are per-run, opt-in and easy to omit.

ADR 0004 is worth re-reading here. The archived Rust engine bounded exactly this step with plan_bpe_sample: a 16 MiB sample split in proportion to each dataset's size, with a 5% floor per dataset. The ADR also records that raising that sample to 64 MiB moved held-out bytes/token by less than 0.5% — inside noise, at 4× the cost. The Python port kept the streaming half of that design and dropped the sampling half. That is the gap.

One latent cliff worth knowing about

pack.pack reads each source file whole (read_text) and holds its token list on top of the flush buffer. Today the largest file anywhere under input/ or sft/ is 54 MB — and that one is JSONL, which read_conversations reads line by line — so there is no exposure right now. But a single multi-GB .txt dropped into input/root/ would reintroduce the boxed-Python-list blowup that FLUSH_TOKENS exists to prevent, because the flush only triggers between files.

3. Would smaller streams of data help?

This was the specific question, and the honest answer is in three parts.

Where it is already done done

The engine is already packet-oriented everywhere the tokens flow: the 2M-token flush during packing, the per-batch gather out of a memory-mapped corpus, the 1 << 23-token blocking inside frequent_tokens's bincount, line-by-line JSONL reading in read_conversations, the loss buffer that drains once per report window instead of syncing every step. There is no easy win left in the token path — the probe run above spends 681 MB there against a 4.17-billion-token corpus.

Where it would not help no

BPE training. This is the counter-intuitive one. Feeding the trainer the corpus in packets does not reduce its peak, because what is resident is not the text — it is the word→count map over every distinct pretoken seen. Chunk the input into 100 pieces and the map at the end is exactly the same size. The only thing that bounds it is seeing less distinct text, i.e. sampling. That is also why ADR 0004's approach was a sample and not a stream, and why the measured 16 MiB-vs-64 MiB result matters: the composition of the sample is the lever, its size is not.

Training itself. The corpus is already consumed a batch at a time; the constraint is the 8 GB of VRAM on the 3060, and that run used 383 MB of it. Splitting the data further would change nothing and would cost the seeded per-epoch shuffle its document granularity.

Where sampling does help, and by how much measured

The diagnostics histogram. Measured against the full 4.17B-token result:

SampleTimeTop-32, exact order Top-32, same set
whole corpus64.1 s32/3232/32
first 10M tokens0.1 s3/3223/32

Note what the prefix rows say. Reading the first 200M tokens — five times more data than the 1-in-64 stride — gets only half the right token set, because the corpus is laid out in dataset and stage order: the head of the file is one body of text, not a sample of the corpus. "Process one packet at a time and stop when you have enough" is precisely the wrong instinct on this file. A stride costs the same page reads spread across the whole file and is exact.

The three fixes, in order of value

  1. Record the token histogram at pack time. Every token id already passes through pack.pack; counting them there costs nothing and writes ~16 KB into segments.json. Training then reads the answer instead of computing it, and the 64 s scan and its 8 GB of resident pages disappear entirely rather than getting cheaper. Same fix applies to sft.py, which already records special_ids_seen this way for exactly this reason.
  2. Build the Collector lazily, or not at all when on_progress is None. It is constructed unconditionally in loop.run, so a run that will never emit a diagnostic frame pays the full cost today.
  3. Bound the tokenizer's input — port plan_bpe_sample from ADR 0004: a fixed byte budget, split proportionally across datasets with a per-dataset floor, strided across each dataset's shards rather than taken from the front. That last detail is the same trap as above, and the ADR records it being hit before: a broken stride meant FineWeb was read from 50 of its 5,498 shards.

If only one of these gets done, make it (3) — it is the only one that is currently capable of taking the machine down rather than merely slowing it.

4. Getting more out of the new WSL config

What the machine now looks like, as measured rather than as configured:

SettingNowAssessment
memory=12GB11 GiB usable, ~1.6 GiB at idle ~10 GiB of working headroom. Enough for everything above except an uncapped tokenizer build.
swap=8GB1.4 GB already in use Useful for parking idle anon memory (backend, dev server) so the page cache keeps the corpus hot. It will not rescue a 15 GB tokenizer build — it will turn an OOM into an hour of thrash on a vhdx.
processors=6torch.get_num_threads() == 6 free win Measured on an 866 MB tokenizer build: 6 threads = 46.4 s / 1,577 MB, 2 threads = 105.1 s / 1,528 MB. 2.3× faster for 3% more RAM — thread count is not a memory lever here, so use all of them.
Data location/dev/sdd, ext4 vhdx correct Not on /mnt/c. Memory-mapping a corpus across the 9p/drvfs boundary would be catastrophically slow; keep data/ where it is.
vm.swappiness60 tune Too high for this workload. The corpus pages are clean and re-readable for free; the training process's anonymous memory is not. 60 lets the kernel page out the thing that matters to keep cache it can rebuild. Try vm.swappiness=10.
vm.vfs_cache_pressure100 leave it The default is right; page cache over corpus.bin is what makes the memmap design work.
GPURTX 3060, 8 GiB, 1.5 GiB in use Not the constraint at current model sizes (383 MB peak). torch.compile logs "Not enough SMs to use max_autotune_gemm" — expected on this card, not an error.

Concretely

Set the swappiness persistently (systemd is already enabled in /etc/wsl.conf):

# /etc/sysctl.d/99-llm.conf
vm.swappiness = 10

And in .wslconfig, two additions worth making given 51 GB of input and 12 GB of packed datasets:

[experimental]
autoMemoryReclaim = gradual   # hand freed page cache back to Windows
sparseVhd = true              # the vhdx currently only shrinks manually

The honest summary of the upgrade: 12 GB changes which runs are comfortable, not which runs are possible. It buys enough page cache to hold most of an 8.3 GB corpus, which makes the memory-mapped design pay off properly and makes the diagnostics scan survivable rather than fatal. It does not move the tokenizer ceiling, because that ceiling is set by the volume of text selected and grows faster than any RAM you can give WSL on this box. Fix that in the code, per ADR 0004, and the machine you now have is comfortably ahead of the workload.
