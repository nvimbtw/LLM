# Tool Calls

- **Date**: 2026-08-19
- **Status**: Implemented (web search; the seam is built for more)

## Context

The models served here cannot reach anything outside their weights. Adding tool
calls to a model at this scale is not the same problem as adding them to a large
one, and every decision below follows from one fact:

**These models are too small to stop at a tool call.** A large model emits a call
and halts, waiting to be handed the answer. Ours emits a call and carries on
saying whatever it was going to say. Nothing in the grammar can prevent that —
stopping requires the model to have learned that the call is a request rather
than a statement, and at this size it has not.

## Decision

A turn is not generate-pause-resume. It is **generate the whole reply, run
whatever it asked for while it does, then ask again with the answers in the
conversation.**

1. **A marker per tool.** `<|web-search|>query<|/web-search|>`, the marker stem
   being the tool's name on the wire. Declared once in `engine/llm/chat/tools.py`;
   the grammar, the generation loop and the SFT renderer all read that table, so
   a new tool is two reserved slots and one row.
2. **The result is a third role**, sitting between the assistant turn that
   called and the one that uses it — the position the system block occupies at
   the front of a conversation. Stored as a `tool` message, never a training
   target, and forbidden to the model by the grammar.
3. **The engine detects, the backend executes.** The generation loop emits a
   `tool_call` SSE frame the moment the closing marker is sampled; the Rust side
   owns the API key, the HTTP call, and the round loop.
4. **Execution overlaps generation.** A tool is spawned on its call and joined at
   the end of the reply, so a ten-second search runs under the tokens that
   follow it rather than after them.
5. **The round loop is bounded** (`MAX_TOOL_ROUNDS`), and each `done` frame is
   stamped `final` so the client can tell a round's end from the turn's.

## Rejected alternatives

- **A generic `<|tool|>name:arguments<|/tool|>`.** Cheaper in reserved slots —
  23 were free, and a marker pair per tool spends two of them. Rejected because
  a model this size cannot reliably spell a tool name and then an argument in
  one string, and because a generic marker gives the grammar nothing to police:
  with a dedicated pair, `Rules` can refuse a call inside a code block and
  refuse a tool that does not exist, before either reaches the backend. One
  embedding row per tool beats a name the model has to compose from merges.

- **The backend scanning the token stream for markers.** This was the first
  design, and it is what the marker *looks* like it invites. Rejected because
  the backend receives decoded text in byte-level fragments: a marker arrives
  split across chunks and has to be reassembled with a partial-marker buffer,
  for no gain. The generation loop already has the token ids and the block
  stack. Detection belongs where the ids are; execution belongs where the API
  key is.

- **The engine executing the tool itself.** It is one process closer to the
  work. Rejected because it inverts the arrow the whole system is built on —
  requests flow frontend → backend → engine — and because it would put a
  third-party API key and outbound internet access inside the process holding
  the GPU.

- **Retraining tokenizers to adopt the new markers.** Simpler: no migration
  script. Rejected because the special block is a fixed 64 slots padded with
  placeholders precisely so this is unnecessary — a vocabulary saved before a
  marker existed already has that marker's id. Adoption is a rename
  (`scripts/relabel_reserved_slots.py`), ids do not move, corpora stay valid and
  checkpoints still load.

- **Brave Search as the only provider.** It was the first one built, and the
  seam is unchanged by the swap — but a hosted search behind a metered key is a
  poor default for a project whose whole point is running the stack yourself.
  Brave's free allowance is $5/month of credits (about 1,000 requests) and
  signing up requires a card even for those. SearXNG is now the default and
  Brave the fallback: `deploy/searxng/` is a compose file and a settings patch,
  and `SEARCH_URL` beats `SEARCH_API_KEY` when both are set. Both stay, because
  two providers behind one `Tool` is the demonstration that the trait was worth
  having.

- **Failing the turn when a tool fails.** Rejected: the reply is already
  generated by the time the tool is awaited, and a reply the person never sees
  because a search returned 429 is a worse outcome than one that says the search
  failed. A failure becomes a `<|warn|>` the model reads. A tool with no
  credentials is not registered at all, so chat works on a checkout with no keys.

## Consequences

- One turn is stored as three rows (`assistant → tool → assistant`). That is the
  right shape for the model, whose next prompt must contain all three, and the
  wrong shape for a reader — so the frontend folds them back into one message
  with a trace (`hooks/use-chat.ts::groupTurns`).
- `chat.stream` yields `(kind, data)` rather than a bare token dict, because it
  now has two frame kinds to emit.
- A tool's answer is text a stranger wrote going into a prompt. Every tool runs
  it through `tools::markup::neutralize`; the Python scraper's equivalent needed
  `-` added to its marker pattern, without which `<|web-search|>` in a scraped
  page would have tokenized as a real marker.
