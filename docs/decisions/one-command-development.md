# One command to start everything — and why it is not one container

**2026-08-24**

Starting a day's work meant four things in three places: `cargo run --release`
in one tmux pane, `bun run dev` in another, and two containers started by hand.
That is fine for one person who set it up and untenable for anyone else — and
the people about to help here do not use tmux.

`docker compose up` is now the whole sequence.

## One container was the obvious answer and the wrong one

The instinct was a single container running everything, on the grounds that one
container is one command. It is, but the command is not the thing that was
expensive — the *coupling* was. A single container running all five processes
means restarting the frontend to pick up a CSS change also restarts Postgres,
SearXNG and a Python engine that takes a minute to import torch. That is the
problem the tmux panes were already solving, reintroduced.

Compose gives the same single command without it. `docker compose up` starts
everything and interleaves the logs, colour-prefixed by service, in one
terminal; no multiplexer is involved and nothing has to be learned to read it.
`docker compose restart backend` restarts exactly one thing. That is strictly
better than what the tmux setup offered, not a compromise against it.

Rejected along with it: a process manager (`overmind`, `mprocs`) over native
processes. It solves the pane problem and none of the install problem — a new
contributor still needs Rust, Bun, Python 3.13, a Postgres server and two
virtualenvs before the first run.

## What it cost

Three things had to change, and each is a fact about this project that was
previously implicit.

**The query macros needed an offline cache.** sqlx checks every query against a
live schema at compile time, and a Docker build stage has no route to the
`postgres` service. `.sqlx/`, generated by `cargo sqlx prepare --workspace`, is
now checked in and the images build with `SQLX_OFFLINE=true`. It is regenerated
whenever a query or a migration changes — if the container build fails while
`cargo run` on the host still succeeds, that is what happened. This was worth
doing regardless: it is also what makes a CI build possible without a database.

**The server no longer hard-codes its binding.** `.bind(("127.0.0.1", 8080))`
made the published port unreachable, because a container's port mapping cannot
reach a loopback binding. `BIND_ADDR` defaults to `127.0.0.1`, so a native run
is unchanged, and compose sets `0.0.0.0`.

That binding was load-bearing: `BACKEND_SERVICE_SECRET` unset leaves `/internal`
open, and the loopback binding was what kept that private. So the compose file
**requires** the four service secrets rather than defaulting them — it refuses
to start without them, and `.env.example` says why. The bargain the native setup
strikes is not available to a container and the configuration should not pretend
otherwise.

**The engine is in the default profile despite its size.** It was going to sit
behind `--profile engine`, so a contributor fixing the UI would not download
several GB of torch and CUDA wheels. That does not work: `main.rs` `expect()`s
on `Supervisor::start`, and with autostart off that is a hard failure when
nothing answers at `ENGINE_HOST`. A default profile without the engine is a
default profile where the backend exits at boot.

The alternative was making an absent engine a warning and letting engine-backed
routes 503. Rejected: it converts a clear failure at startup into an unclear one
per request, to save a download that happens once. The image is built once and
cached; the boot contract is read by everyone forever.

## A bind mount does not honour `.dockerignore`

`.dockerignore` filters the **build context**. It has no bearing on what a bind
mount exposes at runtime, and the two lists are easy to conflate because they
name the same directories.

Both build outputs had to be masked with a volume over the bind mount for this
reason. `node_modules` because bun resolves some packages per platform. And
`.next`, which cost an afternoon: a tree built natively carries the host's
absolute paths inside `required-server-files.json`, so Turbopack in the
container resolved against `/home/<user>/…`, found nothing, and reported
`Next.js package not found` with version `0.0.0` — a missing-package error for a
package that was present and correct the whole time.

The engine and data engine carry the same hazard in `__pycache__/`, unmasked.
Python revalidates a `.pyc` against its source's mtime, so it has not bitten;
it is the first thing to suspect if an import there ever misbehaves.

## What is deliberately still bind-mounted

`engine/data/` — corpora, vocabularies and weights — stays a host directory. It
is hundreds of MB that belong to the machine rather than to a container that
gets recreated. `torch.compile`'s Inductor cache gets a named volume for the
same reason in reverse: nothing on the host wants it, and without it the first
training step after every `up` pays full compilation cost again.
