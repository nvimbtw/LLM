# Codebase audit — 2026-10-13

The module ownership boundaries are useful. The implementation does not yet
consistently preserve them through cancellation, retries, account changes and
resource eviction. The largest quality problem is lifecycle logic distributed
across database functions, worker registries, HTTP handlers, sockets and hooks.
Smaller functions will help only if those responsibilities become explicit.

Discussion: [Discord DOC-4](https://discord.com/channels/1538659898383011961/1559534257695891487).
The companion [agent-rule proposal](2026-10-13-agent-rules.md) contains proposed
policy text, adopted in AGENTS.md and the active conventions after author approval
on 2026-10-13. Findings below remain the audit-time snapshot.

## Scope and confidence

Inspected the current working tree, based on HEAD `127f098`, including substantial
uncommitted and untracked ownership/scheduling work. Coverage includes all six
modules, service adapters, authentication, conversation/tool protocols, training
and recovery, corpus caches, benchmark scoring, gym state, deployment, migration
and preparation scripts, tests, and agent documentation. This is a broad,
risk-focused source audit, not a claim that every line has been exhaustively
verified or that the system is free of other defects.

The source inventory contains 541 files and 87,859 lines, excluding tests,
migrations, generated assets and experiment directories. Counts include scripts,
frontend GPU source and declarations. File length is a triage signal, not proof
that a module needs splitting.

Evidence is labelled **reproduced**, **source-confirmed**, or **needs runtime
confirmation**. Reproductions used throwaway state. Astra reviewed the difficult
execution/cancellation and RL-estimator questions. No application fixes,
migration execution, commits, pushes or Docker operations were performed.

P1 means address before trusting the affected workflow or exposing it beyond a
trusted local audience. P2 means a concrete reliability, scientific-correctness
or maintenance issue to schedule next. Priorities describe impact, not urgency
to rewrite unrelated code.

## Correctness and reliability findings

### F01 · P1 · SFT cache identity omits the vocabulary

**Source-confirmed.** `llm-engine/llm/corpus/sft.py:74` keys a packed dataset by
selection and reasoning policy only. `is_built` at line 492 checks the same
information. `llm/orchestrate/sft.py:195` loads the selected base's tokenizer but
reuses that cache without comparing it. Fine-tuning two independently tokenized
base models on the same conversations can train the second on the first
vocabulary's token IDs. Equal vocabulary sizes make this silent; different sizes
can also produce invalid IDs.

**Solution:** include a canonical tokenizer fingerprint and chat-renderer
version in the key and sidecar; validate both before reuse. Treat old sidecars
without those fields as a cache miss. Pretraining's fingerprint check is an
existing local precedent.

**Regression:** build the same conversation with two equal-sized vocabularies
whose ordinary-token IDs differ. Assert separate caches and decoded-text parity
under each vocabulary; changing the renderer must invalidate reuse too.

### F02 · P1 · An accepted cancellation can disappear before work starts

**Reproduced in isolation.** `llm-engine/api/runner.py:97` commits cancellation
before looking for a live event; `_claim` at line 145 commits running before
`_execute` adopts a fresh event at line 162. A cancellation between those stages
returns success, finds no event, and the handler subsequently runs with a clear
flag. Final completion overwrites the cancelling status. Data-engine has the
same claim/adopt pattern. Claim and cancel also need concurrency control on
their database transitions.

**Solution:** use conditional transitions or row locks and reconcile persisted
cancellation when adopting, before computation starts. Give one execution
coordinator ownership of the durable state and live cancellation handle.

**Regression:** pause between claim and adoption, cancel from another thread,
then resume. Assert the handler does not run and the final row is cancelled.
Astra's production-code probe printed `cancel accepted True`, followed by
`cancel final done handler cancel flags [False]`.

### F03 · P1 · Follow-up chains can remain waiting forever

**Reproduced in isolation.** `llm-engine/api/chain.py:30` resolves only direct
dependents. If A fails, B becomes failed while C continues waiting on B.
`api/runner.py:104` returns immediately for queued/waiting cancellation without
resolving dependents. `main.py:30` calls `store/queries.py:310` restart cleanup
without reconciliation. Completion and promotion are separate transactions,
leaving another crash window.

**Solution:** implement idempotent dependency reconciliation over all terminal
parents, cascading unsuccessful outcomes and releasing successful ones. Run it
after every terminal transition and at startup. Prefer a transaction covering
parent completion and immediate dependency updates; retain reconciliation for
crash recovery and legacy state.

**Regression:** a three-step failed chain, queued-parent cancellation, restart
during a parent, and restart after completion commits but before promotion.
Astra reproduced `failed failed waiting` and `failed waiting` states.

### F04 · P1 · Benchmark control failures abandon live GPU work

**Source-confirmed failure path.** After dispatch,
`llm-engine/api/handlers.py:278` treats a failed status poll as job failure,
without retry, remote cancellation or reconciliation. The benchmark can keep
running after the queue reports failure and refuses further cancellation.
`bench-engine/bench/runner.py:20` has a 3,600-second measurement timeout;
`bench-engine/main.py:84` removes the active cancellation handle after errors,
without stopping the remote synchronous measurement. Restarting bench-engine
can leave the measurement alive in the separate LLM process as well.

**Solution:** retain execution ownership through uncertain transport outcomes.
Reconcile idempotent execute/status requests, then signal and drain remote
cancellation before making the queue terminal. Measurement disconnect/deadline
handling must set its cancellation event while preserving the device gate until
the worker actually stops.

**Regression:** admit a blocked fake measurement, inject a failed status poll or
measurement-hop timeout, and verify it receives cancellation before the queue
relinquishes ownership. The single-worker device gate itself appears sound: it
prevents simultaneous computation, but abandoned work can still block the queue.

### F05 · P1 · A queued job's detail page does not follow its execution

**Source-confirmed.** `frontend/hooks/use-job.ts:236` fetches once and line 258
attaches once. `lib/jobs-socket.ts:56` turns the queue's one-shot `state` frame
into `onInactive`; the hook supplies a no-op. Nothing polls or reattaches when
queued/waiting becomes running. The separate board poll does not update this
hook's job. A page opened on queued work can remain queued until reload. Line
263 also refreshes only for done/error, although the socket closes on cancelled.

**Solution:** observe authoritative job status while nonterminal, attach when
running, refresh on all terminal events, and reconcile after unexpected socket
closure. Store telemetry by job ID so client-side navigation cannot carry the
previous job's chart state into the next one.

**Regression:** open queued job detail, start it elsewhere, cancel it elsewhere,
and verify all transitions without reload. Navigate directly between two jobs
and assert no telemetry crosses IDs.

### F06 · P2 · Multiple interjections are acknowledged incorrectly

**Reproduced with the production frontend callback.**
`backend/crates/api/src/turn.rs:139` joins buffered messages with blank lines.
`frontend/hooks/use-chat.ts:678` removes a queued message by exact string match.
Acknowledging `first\n\nsecond` removes neither `first` nor `second`; both can be
sent again by `drainQueued` after already influencing the continuation.
The backend also sends `interjected` at line 123 before the next round's
`conversation::prepare` persists it, so subsequent failure can lose an
already-acknowledged message.

**Solution:** carry interjection IDs through the protocol, persist ordered IDs
and content, then acknowledge the committed IDs. Make replay idempotent.
Content is not message identity.

**Regression:** queue two different messages and two identical messages during
one round; each must be applied once. Inject storage failure before commit and
assert no acknowledgement is emitted. The extracted production callback retained
both queued IDs after receiving the combined acknowledgement.

### F07 · P1 · Account providers can expose and persist the previous account's state

**Source-confirmed.** `frontend/components/settings/settings-provider.tsx:94`
keys loading by an authenticated boolean and retains the previous settings in
memory. On another login, line 158 exposes those settings immediately. A failed
GET preserves them, then line 125 marks loading complete, allowing the next
change to PUT the old account's full settings, including its system prompt,
under the new token. `chat/chats-provider.tsx:120` similarly retains titles;
`chat/composer-choice-provider.tsx:84` retains the old choice, even when the new
account returns an empty choice. A token replacement that stays authenticated
does not rerun these effects at all.

**Solution:** key all private state, pending writes and responses by a session
identity/generation. Expose defaults or loading until data for that identity
exists; reject stale responses and writes. Failed loads must not authorize
overwriting unknown server state. Reuse the token-aware isolation already
implemented in `lib/chat-history.ts`.

**Regression:** load A, log out, log into B with delayed/failed GETs, and edit a
setting. Assert no A titles, prompt or choice is visible or written for B.
Also replace one non-null token with another while providers stay mounted.

### F08 · P2 · Data run and dataset state disagree on failure, cancel and restart

**Reproduced with production data-engine code and SQLite.**
`data-engine/api/handlers.py:129` lists shards outside its failure cleanup.
`api/runner.py:79` cancels queued rows without settling the target dataset.
`store/queries.py:446` marks every pulling dataset failed at startup, including
targets of queued runs deliberately left queued. Dataset creation and enqueue
also commit separately in `api/routes/datasets.py:142` and line 205.

Observed: queued cancellation yielded `run=cancelled dataset=pulling`; injected
listing failure left `dataset=pulling`; startup reconciliation yielded
`run=queued dataset=failed`.

**Solution:** create dataset and job atomically; centralize terminal settlement
of the target dataset, including failures before iteration and queued cancels.
Restart cleanup must settle only abandoned work or derive status from its job.
Preserve partial counts deliberately.

**Regression:** exercise each observed sequence, enqueue failure, missing source
before processing, and deletion during processing. No terminal run should leave
its target indefinitely pulling.

### F09 · P2 · Live registries retain every finished run and unbounded backlogs

**Reproduced.** `llm-engine/api/runs.py:60` and
`data-engine/api/runs.py:59` retain all adopted runs; finish never evicts them.
Every frame remains in `history`, and each subscriber uses an unbounded queue.
A production data registry retained 1,000 terminal runs after 1,000 completions.
Deleting a durable job does not remove that memory. Frontend chart caps do not
bound backend retention.

**Solution:** keep active runs plus a bounded terminal TTL/LRU cache. Compact
telemetry into bounded snapshots/series. Use bounded subscriber queues with a
documented resync or slow-consumer policy and preserve terminal delivery.

**Regression:** execute many runs and attach a slow subscriber; assert bounded
retained bytes/entries and a usable terminal or resync response.

### F10 · P1 · Ordinary inference lacks a useful resource ceiling

**Source-confirmed.** `llm-engine/llm/config.py:559` permits an arbitrarily large
finite context multiplier; `llm/orchestrate/chat.py:197` allocates the extended
RoPE table from it. The public authenticated chat path accepts this value.
Message/token counting and generation also need explicit service-level budgets;
a UI slider is not request validation. `backend/.../routes/stream.rs:220` uses
an unbounded interjection channel and has no aggregate interjection budget.

**Solution:** define server-owned limits for effective context, output tokens,
input bytes and buffered interjections; reject out-of-range/non-finite values
before counting or allocating. Bound waits and authenticated socket admission.
Keep configuration defaults and resource safety limits distinct.

**Regression:** submit huge finite multipliers, invalid token budgets, many
interjections and stalled handshakes; assert bounded resource use and explicit
client errors without GPU allocation or a worker panic.

### F11 · P1 · Deleted users and changed passwords do not invalidate access tokens

**Source-confirmed.** `backend/crates/api/src/extractors.rs:19` verifies signature
and token claims without checking current account/session state. Admin access
comes from the embedded claim. `auth/src/token.rs:31` issues 24-hour tokens;
`api/src/routes/user.rs:237` deletes the account, and password updates similarly
change no token/session generation. A deleted administrator's previously issued
token can still pass AdminUser and call admin proxy routes until expiry.

**Solution:** use revocable sessions or an account auth-version checked during
HTTP and socket authentication. Revoke on deletion/password reset and derive
authorization from current account state. Define the treatment of already-open
sockets explicitly.

**Regression:** issue admin/user tokens, delete the account or reset its password,
then exercise HTTP and socket authorization with those tokens. They must fail.

### F12 · P2 · Gym workspace lifetime is shorter than the stored episode lifetime

**Source-confirmed.** `gyms-engine/api/routes/gym.py:122` seeds every episode
before the run starts. `deploy/just-bash/server.mjs:58` silently expires/evicts
sessions and recreates an empty filesystem. The 256-episode maximum matches the
entire default sandbox capacity, leaving no room for another run or chat.
Creating two pending runs, or waiting past TTL, can remove a future episode's
files while its database record still claims its environment is prepared.

**Solution:** give episode workspaces explicit leases/capacity admission and
report environment loss as infrastructure failure. Seed unopened episodes at
admission or regenerate them deterministically; never silently reset an active
episode whose filesystem mutations are part of grading.

**Regression:** exceed sandbox capacity with two pending runs and expire an
episode before its first command. Assert reseeding or an explicit infrastructure
outcome, rather than grading the model against an empty workspace.

### F13 · P2 · Gym database checks do not serialize external actions

**Source-confirmed race.** `gyms-engine/api/routes/gym.py:235` checks episode
status and computes the next step before executing the shell, without locking
the episode. `store/queries.py:112` recomputes the step number when recording.
The unique constraint catches some duplicate writes after commands have already
run; it cannot undo shell effects or guarantee reward correctness. Concurrent
finish calls also compute run aggregates before serializing the run update.

**Solution:** claim an episode operation with a request ID and explicit
in-progress state, serialize actions per episode, and make completion/retry
semantics deliberate. Lock the run while settling aggregates or compute them
at read time. A database transaction alone cannot make a remote shell atomic.

**Regression:** race two steps on one episode and two finishes on different
episodes using separate PostgreSQL connections. Assert command count, order,
reward totals and aggregates match the durable trajectory.

### F14 · P2 · RL's policy mask includes forced tokens and omits sampled stops

**Source-confirmed.** `llm-engine/llm/train/rollout.py:139` appends forced closing
markers to `produced`; line 357 marks the entire produced list as drawn.
Sampled stop markers are discarded at lines 189–191. The policy objective at
`train/policy.py:163` promises that only drawn tokens carry loss, but its mask
does not represent the sampled actions.

**Solution:** record token IDs and action provenance together. Forced grammar
repair/scaffold gets no policy loss; sampled stop decisions should be represented
consistently in the objective and subsequent prompt construction.

**Regression:** truncate with open markup and stop naturally in another rollout.
Assert forced closers have false policy flags and sampled stops have the intended
trainable action representation.

### F15 · P2 · The claimed on-policy estimator uses a different distribution

**Source-confirmed; mathematical review by Astra.**
`llm-engine/llm/train/rollout.py:182` applies grammar/tool masks and truncated
sampling. Defaults include top-k 40/top-p .95 (`llm/config.py:424`).
`train/policy.py:141` computes raw, unfiltered log probabilities and lines
187–199 use them for the advantage objective. Identical weights do not make the
raw model distribution identical to the constrained behavior distribution.
The sampled KL penalty has the corresponding measure mismatch.

**Solution:** explicitly document this as a biased advantage-weighted raw-token
surrogate, or define the sampler as the policy and replay its support,
temperature and normalization for differentiable log probabilities. Omitting
clipping for one update is a separate, defensible choice; adding clipping does
not repair this problem. Disabling top-k/top-p alone leaves grammar masking.

**Regression:** at a later history with exactly one permitted token and nonzero
advantage, the constrained policy gradient should be zero. Compare reconstructed
probabilities with the sampler under non-unit temperature and truncated support.

### F16 · P2 · Streaming assumes decoded prefixes never change

**Algorithm counterexample; real tokenizer runtime still needs confirmation.**
`llm-engine/llm/orchestrate/chat.py:245` emits
`decode(all_ids)[len(decode(previous_ids)):]`. Replacement decoding of an
incomplete UTF-8 sequence is not prefix-monotone: byte prefixes C3 then C3 A9
decode to replacement-character then `é`. This expression streams the replacement
character and no correction, while the final content is `é`. The audit probe
confirmed that counterexample with ordinary UTF-8 replacement decoding; the
installed host environment lacks tokenizers for an end-to-end assertion.
Repeatedly decoding both full prefixes also introduces quadratic decode work.
Line 212 additionally treats valid seed 0 as absence.

**Solution:** use incremental decoding with buffered incomplete bytes, or a
protocol supporting text replacement offsets; emit committed deltas only. Use
`seed is not None`. Preserve special-token semantics.

**Regression:** force byte-split accented characters/emoji and literal replacement
characters; concatenated deltas must equal final content. Seed 0 must reproduce
the same draw. Benchmark long output to detect repeated full-prefix decoding.

### F17 · P2 · Unpublishing does not implement documented visibility

**Source-confirmed.** `backend/crates/api/src/routes/models.rs:16` forwards any
authenticated user's model listing unchanged; `llm-engine/api/routes/models.py:33`
defaults to include_private. `frontend/hooks/use-models.ts:269` filters only for
parameters, and the grid's initial visibility is all. The composer also uses that
list. Even setting include_private=false is insufficient if the service's disk
join reintroduces unpublished directories as rowless entries.

**Solution:** enforce discovery policy on the server and apply it to both halves
of the disk/row join. Decide and document whether publication also grants direct
inference/detail access; implement that decision consistently rather than
assuming hiding a toggle enforces it.

**Regression:** an ordinary user must receive the intended published-only list
and picker options; explicit query parameters must not widen their permissions.
Check direct access separately against the chosen policy.

### F18 · P2 · Abandoned and late-finishing uploads accumulate

**Source-confirmed.** `frontend/components/chat/chat-composer.tsx:330` revokes
object URLs on unmount but does not discard stored rows. At line 376 an upload
finishing after its tile was removed calls `settle` on a missing entry and leaves
the returned attachment unclaimed. Backend attachments have no expiry/quota
cleanup path. A per-file 50 MiB bound does not bound abandoned storage.

**Solution:** model staged uploads with an expiry and server-side sweep. Cancel
or discard late results when their draft no longer exists; preserve uploads
explicitly handed to a pending send. Apply per-owner storage/concurrency budgets.

**Regression:** remove a file while upload is pending, navigate away from a draft,
and close the browser after upload. Assert staged rows expire while bound files
remain intact. Keep React state updater functions free of deletion side effects.

### F19 · P2 · The final chat round can execute tools whose results are discarded

**Source-confirmed.** `backend/crates/api/src/turn.rs:210` starts tools even when
last_round is true, and line 216 marks the answer final. The client closes on
that frame; the loop can still wait for or run the tool with no continuation
round available. A tool with filesystem effects can change state after the user
has been told the turn ended. The gym path already masks calls on its terminal
round.

**Solution:** pass max_tool_calls=0 for the terminal chat round and defensively
refuse late tool starts. Define whether the configured bound counts generated
rounds or tool continuations, then test that contract.

**Regression:** make the model request bash on the last round; assert no shell
action occurs after final and the final reply is a terminal answer.

### F20 · P2 · Preparation scripts write into a retired data tree

**Source-confirmed.** `scripts/paths.py:28` resolves DATA to `engine/data`, while
the active module is llm-engine and training text belongs to data-engine's DB.
Its docstring still advertises input/sft folders as selectable training sources.
`scripts/prepare_eval_corpus.py:34` uses that helper, while bench-engine reads
`bench-engine/data/corpus` or BENCH_CORPUS_DIR. Preparation can succeed while
producing data no active consumer reads.

**Solution:** separate acquisition outputs from service storage. Make preparation
produce an explicitly chosen import/export artifact, wire training imports
through Rust/data-engine, and give evaluation preparation the bench-owned output
path. Deprecate legacy scripts with an actionable error if they are unsupported;
simply renaming engine to llm-engine would preserve the ownership mistake.

**Regression:** run preparation against a tiny local fixture and verify the
documented consumer reads its output. No production downloads are needed.

### F21 · P2 · Benchmark corpus limits and provenance are incomplete

**Source-confirmed.** `bench-engine/bench/corpus.py:55` reads and concatenates
every reference file before applying its size caps. Those caps slice Python
characters despite being named bytes. `bench/runner.py:16` stores neither corpus
content hash nor split/prompt manifest in the report. Editing a local corpus can
therefore change the meaning of a score while leaving suite/version identical.

**Solution:** select bounded UTF-8 slices without materializing the whole corpus;
define the split and units precisely. Save corpus/split/prompt hashes, scorer
version and resolved sampling configuration in immutable report provenance.
Compare historical measurements only when their manifests are compatible.

**Regression:** use large files and multibyte text to assert memory/byte bounds;
alter one reference file and assert the manifest changes and comparison is
flagged. Keep unavailable language measurements explicit.

### F22 · P2 · Password hashing blocks HTTP workers

**Source-confirmed.** `backend/crates/api/src/routes/auth.rs:40` verifies Argon2
synchronously inside an async handler; user creation and password updates also
hash inline. Multiple unauthenticated login/signup requests can occupy Actix
workers with CPU/memory-heavy work. No admission/rate-limit layer is configured
in `backend/src/main.rs`.

**Solution:** move password work onto a bounded blocking executor and apply
authentication-specific rate/concurrency limits. Bound the expensive work rather
than relying solely on password length validation. Keep error responses uniform.

**Regression:** issue concurrent password operations alongside a cheap health
request and assert the HTTP executor stays responsive and hashing concurrency
does not exceed the configured bound.

## Code-quality assessment

### Q01 · Function size rules miss the places that most need them

The current R1 scope is Rust. Python and React have grown the largest control
flows: `llm/train/loop.py:308` is 341 lines, `_finetune` is 208,
`llm/corpus/sft.py:222` is 192, `frontend/hooks/use-chat.ts` is 858 lines and
`components/chat/chat-composer.tsx` is 1,212. These orchestrate multiple lifetimes
and mutate state across large closures. More names alone will not reduce that
coupling.

Extract by owned behavior: optimizer setup/update; batch/cursor iteration;
progress assembly; checkpoint publication; chat event reduction; transport
lifetime; upload lifecycle; dictation/editor integration; slash-command
execution. Keep a short orchestration function that makes their order visible.
Use a small session/context type when several operations share one coherent
lifetime; do not replace ten arguments with an untyped service locator.

### Q02 · Typed boundaries disappear at orchestration seams

Opaque JSON is useful for genuine pass-through routes. It is unsuitable once
Rust interprets chat inputs, prepared turns, inference completion and output
identity (`api/src/conversation.rs`, `turn.rs`). Python similarly passes broadly
typed dicts/Any through runner handlers and result detection. Frontend event
handlers assert arbitrary records into training types and retain unused legacy
snapshot/chat cases.

Define small DTOs and discriminated event/result variants at interpreted seams.
Validate once, translate once, then use typed domain values internally. Preserve
an explicit extension field where forward compatibility is required. Generate
wire schemas or use shared fixtures for protocol contracts; do not recreate each
request independently in Python, Rust and TypeScript.

### Q03 · Similar service runtimes have already drifted

The auth files, Hop clients and registry/runner infrastructure are copied across
services. Data runner wake-up, terminal settlement and thread-to-loop handling
already differ from the LLM runner. Bench's Hop docstring describes LLM dataset
and gym traffic. Four copies of generic transport policy create four chances
to get authentication, timeout and error behavior wrong.

First align the contracts and their tests. Then extract a small versioned shared
Python transport/runtime package only for stable common behavior. Inject audience,
issuer, session factory and domain callbacks. Keep GPU admission, dataset
settlement and benchmark dispatch in their owning services; avoid a universal
job framework with flags for every difference. Python services still communicate
only through Rust.

### Q04 · The new conversation SQL is compressed rather than readable

`backend/crates/db/src/conversation.rs:40`, line 117 and line 146 compress
substantial queries and mapping into very long lines. Short line counts hide
join, ordering, ownership and aggregation semantics. `position = max + 1` also
rescans chat history on every append; list/get/history fetch all relevant rows
without a pagination contract. Conversation preparation loads the entire history
before applying a floor.

Format SQL as SQL. Use named enums/newtypes for role/feedback/request identity,
explicit repository queries and typed view mapping. Introduce cursor pagination
and bounded context-history reads; consider a locked next-position counter when
measurements justify it. Retain compile-time query validation and regenerate
SQLx metadata with actual query/schema changes.

### Q05 · Resource ownership is implicit in globals and callback order

Bench creates its executor and active map at import time. Model gates, registries,
frontend caches, provider timers and socket handles rely on global or ref state.
Several lifespans cancel an asyncio task without awaiting it or ensuring a
threaded worker has stopped. Import-time executor shutdown also complicates
multiple app lifespans in tests.

Create an application runtime at startup with explicit start/stop and bounded
ownership. Inject it into handlers. Give every worker/socket/timer/file/cache a
documented owner and completion policy. Await shutdown, signal cooperative
cancellation and distinguish a cancelled waiter from a stopped worker. Keep
hot-path allocation and tensor behavior unchanged during structural refactoring.

### Q06 · The checks under-enforce the rules and miss transition contracts

There is no checked-in CI workflow or single cross-module verification entry
point. Python configs contain pytest/coverage settings and minimal pyright venv
configuration, without an enforced formatter/linter/typecheck gate. Frontend
lint is stock Next/TypeScript configuration and does not enforce most bespoke
structure rules. Rust build passes while fmt and strict Clippy fail.

The 25 frontend tests cover plans, chat-history caching and art, not job-detail,
account provider or interjection transitions. Bench's ten tests cover history
and scoring, not dispatch/cancel/restart. SQLite checks do not exercise the
PostgreSQL concurrency behavior this system relies on. LLM coverage config
names llm/main, omitting api/store from its measured source set.

Add a documented, reproducible verification command and CI with pinned tool
versions. Prioritize lifecycle, concurrency and cross-language contract tests
from F01–F22. Use a disposable supported PostgreSQL instance for integration
tests. Establish a baseline for legacy lint debt; do not hide it behind blanket
ignores or require an unrelated cleanup in every feature change.

### Q07 · Documentation volume and narration obscure contracts

`docs/frontend/README.md` is 1,755 lines; backend's is 659. Both exceed the stated
approximately 250-line map target. LLM's README still has TODO stack/conventions
sections and describes retired Ask/conversation routes. Its generic-tool section
says adding a tool consumes reserved slots, contradicting the adjacent generic
marker design. Backend says data reads are owner-scoped, while actual dataset
reads are shared. Choose and document the shared policy rather than implying
isolation. Comments frequently retell earlier implementations or deleted paths,
including the old attachments route/eleventh-file cap in `lib/attachments.ts`.

Make each module README a short current boundary/invariant/map. Move substantial
UI, telemetry and operational topics to sibling pages; retain decision rationale
in dated records. Replace bug-history narration in function bodies with regression
tests and concise function-level documentation. The author's subsequent review
requires brief purpose/input/output documentation for each named function and no
explanatory comments inside its implementation. Move useful math, safety, units
and protocol explanations into that function's documentation rather than leaving
them scattered throughout its body. See the revised agent-rule proposal.

## Refactoring order and acceptance criteria

| Slice | Scope | Acceptance criterion |
| --- | --- | --- |
| 1 | SFT cache identity and RL action provenance | Tokenization identity is checked; sampled and forced actions are distinguished. |
| 2 | Queue transition coordinator and dependency reconciliation | Cancel/claim races, multi-level failure and restart crash windows pass deterministic tests. |
| 3 | Benchmark dispatch ownership | Transport failure cannot leave live work without cancellation/reconciliation control. |
| 4 | Session-scoped frontend resources and job subscription | Account data never crosses identities; queued jobs and all terminal states update without reload. |
| 5 | Identified, committed interjections and terminal tool rounds | Each steering message applies once; no tools execute after final. |
| 6 | Data target settlement and bounded registries | Every job settles its dataset; terminal memory and slow subscriptions remain bounded. |
| 7 | Gym operation ownership and sandbox leases | Concurrent drivers cannot double-run actions; workspace loss never becomes model failure. |
| 8 | Typed orchestration and focused functions | Orchestrators expose order; extracted units own coherent inputs/results and independent behavior tests. |
| 9 | Current docs, rule replacement and automated checks | Rules apply to all languages, are enforceable, and documented commands run against reproducible environments. |

Keep these as focused changes. Establish regression tests before restructuring
numerical code and preserve the pinned dataflow fixture unless a deliberate
behavior change is part of the slice. Do not introduce speculative plugin
systems, repositories/interfaces for every class, or a new service split merely
to make files shorter.
