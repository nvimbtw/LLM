Markers as HTML tags

What the four-part proposal actually costs, what it buys, where it breaks, and the one variant of it I would build instead.

Short version. The instinct is right and the strongest argument for it is already written down in this repo, in a comment nobody wrote for this purpose. But literal HTML tags are the one spelling that cannot work here, for a reason that shows up as a hard number: </a>, <p>, <code> and <li> already appear 7,600 times in a 100 MB sample of the pretrain corpus, and every one of them would silently become a reserved marker id.

What works is HTML shape without HTML names: <m-p>…</m-p>. It is valid HTML5 (custom elements), it collides with nothing, it is styleable by element name — which means proposal 4 disappears rather than getting built — and its closer is </m-p>, which is precisely the spelling scripts/generate_sft_llm.py:373 records teacher models reaching for no matter what the prompt says.

Proposal 3 as written (drop to the opener) conflicts with streaming and, if it is a step toward innerHTML, opens an XSS hole the current parser closes structurally. There is a version of it that is right; it belongs in the engine, over ids, not in the frontend, over text.

1. The four proposals, scored

ProposalVerdictWhy
1. Migrate special tokens to HTML tags right idea, wrong spelling The migration is far cheaper than it looks (§2) and buys a real thing (§3). Literal HTML names collide with the corpus (§4) and only cover 27 of 41 slots (§5).
2. Rewrite the training data cheap and precedented One regex pass over 777 MB of SFT JSONL plus the eval gold and one trace fixture. scripts/migrate_sft_bare_tags.py is the same job, already written, dry-run flag and all.
3. Validate instead of parse; drop unclosed spans breaks streaming; unsafe if it means innerHTML Validation is parsing. Mid-stream every open tag is unclosed, so "drop to the opener" deletes the reply as it arrives. And the grammar already guarantees well-formedness at serve time (§6).
4. Append class="model-*" solves a problem you can delete instead A per-node class only earns its keep if you are building HTML strings. Under the recommended spelling you style m-h1 { } directly and write no classes at all (§7).

2. The migration is much cheaper than it looks — and it does not invalidate a single trained model

This is the part I expected to be the blocker and it is not. Three findings.

Marker ids are positional, so a rename is a pure relabel

special.py:9-11 is explicit that order fixes each marker's id, and SPECIAL_BLOCK = 64 pins the block size independently of how many markers are used. A tokenizer trained with "<m-p>" in slot 1 gives it the same id 1 that "<|par|>" had. An embedding row trained to mean "paragraph opens here" still means that. Renaming in place — never reordering — is a change of spelling only, and the weights are untouched by it.

Existing checkpoints keep working, because each one owns its tokenizer

storage.py:10 — artifacts/models/<id>/ holds "weights, a copy of the tokenizer, meta.json". An already-trained model loads its own copy and keeps emitting the old spellings forever. Nothing on disk breaks.

The one real wrinkle. That cuts both ways: an old model emits <|par|>, and a frontend parser rewritten for the new spelling renders it as visible garbage text. You need either a two-grammar parser (~15 lines: try the new tag shape, fall back to the old one) or an accepted break for pre-migration models. I would take the 15 lines — the model list is the project's history and a review that renders as raw markers is worse than useless.

What does have to be rebuilt, and why it is hours not days

vocab.py:114 records special_tokens_sha() in every build, and matches() at :193 compares against it, so changing the list fails closed into a tokenizer rebuild. The rebuild changes tokenizer.json, so file_fingerprint changes, so corpus_key changes, so every packed corpus re-packs. That cascade is the correct behaviour and it is the whole point of the keying — but note what it costs and what it does not:

  • The re-pack is CPU and disk, not quality. Ids come out the same for the same text.
  • The merge table does shift slightly. The BPE trainer is not given the corpus with markers excised — literal <|par|> bytes in the seeded conversations under Synthetic/ contribute to merge learning today, and different literal bytes will contribute tomorrow. This is a handful of merges out of 8,192, not a different vocabulary.
  • engine/tests/fixtures/trace.json must be re-recorded (python -m tests.fixtures.record), and per CLAUDE.md that diff is the evidence of what moved. Here it moves for a benign reason and the diff should be reviewed as such.

3. The argument for this is already in the repo, written for another reason

This is the finding that changed my mind about the whole idea. From scripts/generate_sft_llm.py:373-377:

# The closer this vocabulary uses is `<|/par|>`. Models reliably reach for the
# XML-shaped `</|par|>` instead — it is the form every other markup language uses,
# and no amount of showing the right one in the prompt fully suppresses it. The
# rewrite is unambiguous and lossless, so repairing beats discarding an otherwise
# good conversation over a transposed slash.

There is a whole repair stage in the SFT generator because the marker grammar fights the teacher model's priors. And the prompt at :281-282 spends two lines pleading:

Closing tags are spelled <|/par|> — the slash goes INSIDE, after the bar.
</|par|> is wrong.

Move to an XML-shaped closer and this entire class of problem stops existing. BAD_CLOSER_RE, repair_markup, repair_conversation and two lines of prompt all get deleted. Teacher compliance on the markup vocabulary goes up for free, which means better SFT data, which is the actual bottleneck on a 30M-parameter model's reply quality. This is a larger win than the frontend cleanliness that motivated the proposal.

Everything below is about preserving that benefit while not paying for it with the corpus collision.

4. Why literal HTML names cannot be the spelling

HuggingFace tokenizers matches added tokens against raw text before pre-tokenization. It does not care whether a match "looks like" markup in context. So the moment "<p>" is a special token, every literal <p> anywhere in the pretrain corpus becomes marker id 1 — inside a code file, inside a StackExchange answer about HTML, inside a tutorial.

I measured it. 200 files per dataset, counting only bare tags (<p>, </a>, … — the attributed forms like <a href=…> would not match and are excluded):

Ranked, over Code + StackExchange: </a> 1,331 · </p> 1,103 · <p> 931 · </li> 593 · </code> 517 · <li> 477 · <code> 450 · </ul> 235 · <strong> 196 · <h1> 109. The four most common are exactly the four most load-bearing markers in the grammar.

Three consequences, in order of how much they should worry you:

  1. Unbalanced markers land in the pretrain stream. Real-world HTML in a code file is fragmentary — a snippet showing </div></p> with no opener. The model would be pretrained on thousands of structurally illegal marker sequences, which is the precise failure docs/decisions/0003 and llm/chat/markup.py exist to stamp out. You would be teaching the disease and treating it at serving time.
  2. The model can never talk about HTML. "How do I write a heading in HTML?" has no representable answer: the reply cannot contain the characters <h1> as prose, because those characters are the heading marker. Given Code and StackExchange are two of nine pretrain datasets, this is a question the model will be asked.
  3. The eval numbers move for a fake reason. eval/markup.py scores false_marker_rate — how often the model wants a marker where prose belongs. Every HTML-shaped token absorbed from Code inflates that. The markup suite would report a regression caused by the rename.

Stripping HTML out of the corpus at prepare time is the obvious counter, and I would not: it means re-preparing 51 GB, and it deletes the content that teaches the model what HTML is.

6. Proposal 3: validate rather than parse

Three separate problems live inside this one, and they want different answers.

Validation is parsing

To know that a tag is unclosed you must track a stack of open tags — which is parseMessage. message-parser.ts is 167 lines including comments and thinking-block handling; the tree walk itself is about 40. There is no cheaper artifact to produce than the tree it already produces.

"Drop to the opener" deletes the reply while it streams

During streaming, every block the model is currently inside is unclosed by definition. A rule that drops back to the opener would make each paragraph vanish the instant it began and reappear only at </m-p> — the opposite of the word-by-word fade in rich-message.tsx:95. Any drop rule has to be gated on the message being complete, and the current renderer already does the right thing by treating a trailing open element as open.

And the case is nearly empty anyway

llm/chat/markup.py masks illegal markers during decoding, and closers() at :222 exists precisely so that a reply truncated by the token cap still drains its stack — "so a truncated reply is still well-formed markup rather than a half-open block the frontend has to guess at". Served replies are already guaranteed balanced. Unbalanced markup reaches the frontend only from pre-grammar stored messages and from unconstrained eval generation. That is worth handling defensively; it is not worth redesigning the renderer around.

If "validate, don't parse" is a step toward innerHTML, stop. Today an element exists only when a reserved token id was emitted — the model physically cannot produce an element the renderer did not sanction, so injection is structurally impossible. Setting innerHTML from model text moves the boundary to string matching, and the model can emit any bytes it likes as prose, including <img src=x onerror=…> learned from the Code corpus. React's escaping is what stands between you and that right now.

Worse, the same text path carries user turns: template.py:132 interpolates user text into the prompt with no escaping, so a user who types the scaffold spelling gets it tokenized as the real marker. That hole exists today with <|/user|>, which nobody types by accident. Rename the scaffold to </user> and it becomes something people paste by accident — which is the second reason the scaffold markers should keep their current spelling.

What I would do instead

Keep the tree. Move the validation to where the ids live:

  • Engine, at generation end. ids_are_balanced(ids, rules) already exists in eval/markup.py:43 and works over ids — no scanning, no ambiguity, no decoder round-trip. Run it on the final reply and record the boolean on the message. It costs one pass over a few hundred ints and gives you a real per-message quality signal in the store.
  • Frontend, on complete messages only. ~10 lines in parseMessage: mark elements the stack never closed, and let rich-message.tsx decide — drop, or render with a muted edge. Rendering it visibly is more useful than dropping it during SFT iteration, and it is one prop either way.

7. Proposal 4, and the design opening it creates

The classes cancel themselves out

class="model-h1" is only necessary if you are handing a browser a string. Custom element names are selectable directly, so under the recommended spelling the stylesheet is:

.reply m-h1 { … }
.reply m-p  { … }

…and no class is ever appended. If you go the other way and keep mapping to semantic elements in React — which you should, for accessibility, since a screen reader knows what <strong> means and knows nothing about <m-strong> — then a scoped .reply strong { } does the same job. Either way proposal 4 is work you can decline.

Be aware of what does not get simpler: the mapping table survives every version of this. Today it maps token name → node type. Tomorrow it maps tag → semantic element (for a11y) or tag → styles. TOKEN_NAME_MAP shrinks from six entries to zero, which is real; the renderer's switch at rich-message.tsx:152 does not go away, because code block needs a copy button and reply needs id resolution. The cleanliness win here is genuine but smaller than it looks from the outside.

The reply surface, editorially

The type scale in globals.css:61-98 already commits to the position — "a page whose largest text is 1.5× its smallest looks like a form no matter what face it is set in" — but the reply renderer does not use it. It sizes in em off the caller (1.5em, 1.25em, 1.08em) and reaches for shadcn tokens that belong to the app chrome. That is why replies read as UI rather than as reading. Four concrete moves, in the order I would make them:

  1. Give the reply a measure. Nothing in RichContent constrains line length. max-width: 68ch on the block is the single largest legibility gain available and costs one declaration.
  2. Let the vertical rhythm come from the elements, not from space-y-3.5. A uniform gap between every child is why a heading, a list and a paragraph currently sit at equal distance. The renderer half-knows this — the heading already carries mt-5 -mb-1 with the comment "a heading belongs to what follows it" — but it is fighting the parent's uniform stack to say it.
  3. Retire the colour on inline code. bg-chart-4/10 … text-chart-4 at rich-message.tsx:176 pulls a chart accent into prose; two words of code in a paragraph become the loudest thing on screen. Editorial minimalism here is a face change and a hairline, not a hue.
  4. Let the code block lose its chrome. Border + tinted header bar + language label + copy button is four devices for one affordance. The label matters only when a language is known; the copy button can appear on hover.

Sketched against the warm-paper palette (#f7f4e4 / #545464), the target is roughly:

Special tokens in the tokenizer

Each protected marker owns a single reserved id, so the assistant marker is one embedding rather than a byte triple the model has to reassemble. That is the whole reason they are worth reserving.

Measure, a real scale, and one weight of emphasis. Nothing here is a new component — it is the same four elements the renderer already emits, set for reading instead of for a panel.

This part is independent of proposals 1–3 and could ship first. It is the fastest visible improvement in the whole document and it needs no retraining at all.

8. Recommendation

Do the migration, with <m-*> spellings, and keep the scaffold as it is.

  1. Markup markers → custom elements, renamed in place so ids are preserved: <m-p>, <m-h1>, <m-strong>, <m-pre>, … Valid HTML5, zero corpus collision, and the closer is the XML-shaped </m-p> that teacher models want to write anyway.
  2. Scaffold and control keep <|…|> — <|user|>, <|assistant|>, <|thinking|>, <|think:med|>, <|endoftext|>. They are not markup, they have no HTML name, and a spelling nobody types by accident is a feature at the prompt boundary.
  3. Add <m-ol> in a reserved slot while the block is open.
  4. Delete repair_markup and the two lines of prompt that fight it. Measure teacher compliance before and after — I expect this to be the biggest single win.
  5. Validate over ids in the engine, record the boolean, and keep the frontend tree. Handle unclosed spans only on complete messages.
  6. Skip the classes. Style by element name or by scoped selector.
  7. Ship §7 first, on its own, before any of the above.

What I would want to see before committing: one dry run of the data migration reporting how many assistant turns change and how many contain marker text that should not be rewritten; and a re-recorded trace.json whose diff is confined to token ids at marker positions. If either surprises you, that is the signal to stop.

9. Honest counter-argument

The case for changing nothing: the current markers are collision-proof by construction, the grammar constraint already guarantees well-formed output, and message-parser.ts is 167 lines that work. The migration costs a tokenizer rebuild, a full re-pack, a re-recorded trace, and a compatibility branch for every existing model — to make the frontend about 60 lines simpler.

On the frontend-cleanliness argument alone, that trade is not obviously worth it. The reason I still recommend it is §3: the teacher-compliance win is a data-quality improvement at the stage where this project is actually bottlenecked, and it is the one benefit that cannot be had any other way.
