Is it really that simple? — reviewing the vision report, and choosing the data

Every claim in vision-support-report.html checked against the files it cites, plus a survey of what Hugging Face actually has for the SFT stage at this model's scale.

Short answer: the trunk half is right, the training half is not. The report's read of transformer.py, checkpoint.py and special.py is accurate, and its central claim — that the decoder, the KV cache, the sampler and the markup grammar are genuinely untouched — holds up. But it costed the training path at 40–60 lines while never opening train/plan.py, and that is where the actual work is: there is no per-example batching in this repo at all. The corpus is one flat uint16 stream sliced into arbitrary [batch, ctx_window] windows, so there is nothing to hang an image on. Its ~400-line estimate is roughly half the real number.

Two of the three "load-bearing edits" in its §7 sketch do not run as written, and its recommended tokenizer change forces a full re-pack of every corpus for no reason — there is a free way to do the same thing. Both are fixed below.

2. The real problem: there is no such thing as a training example here

This is the finding that changes the estimate. The report treats the training change as "batches gain an image tensor; collate onto device." That assumes a batch row is one conversation. It is not.

The corpus is a single flat uint16 array (pack.py, CORPUS_DTYPE). EpochStream shuffles documents and rejoins them with an <|endoftext|> separator, addressing the result lazily. iter_batches then cuts that stream into batch_size × ctx_window contiguous windows:

# train/plan.py — the batching contract, in full
windows = (len(stream) - 1) // ctx_window
span    = batch_size * ctx_window
stream.gather(offset, offset + span + 1, tokens, weights)
yield (tokens[:span].reshape(batch_size, ctx_window),
       tokens[1:].reshape(batch_size, ctx_window),
       weights[:span].reshape(batch_size, ctx_window))

A single row of a batch can hold the tail of conversation A, a separator, the whole of B, and the head of C. Document boundaries and window boundaries are unrelated by design — that design is load-bearing (the comment in EpochStream records that materializing an epoch OOM-killed the engine on the 390M-token corpus, so this is not casually replaceable).

So "attach an image to the batch" has no meaning. What you actually need is a mapping from global token offset → image, resolved per window at gather time, then scattered into the right (row, column) of the embedding tensor. That is a new sidecar format, a change to pack/sft to emit it, a change to EpochStream.gather to carry it through the shuffle permutation (the same way mask already is), and a change to iter_batches' yield signature that every caller must absorb.

The fix that makes this tractable — and it also repairs the loss and the RoPE bugs. Do not concatenate image embeddings at the front. Reserve N placeholder tokens in the corpus itself and substitute the vision embeddings into those positions: 
x = self.embedding(idx)                        # [b, seq, d] — seq unchanged
if images is not None:
    vis = self.vision(images)                  # [n_images, n_patches, d]
    x = x.masked_scatter(slots.unsqueeze(-1), vis)   # slots: [b, seq] bool
# seq, the ctx guard, the RoPE slice, the caches, and _loss are all untouched —
# genuinely this time, because the sequence length never changed.
This is what LLaVA actually does, it is strictly less invasive than the report's version, and it turns three of the report's claimed-but-false "untouched" items into true ones.

3. The tokenizer trap the report walked past

Its plan says to add <|image|> to SPECIAL_TOKENS, taking a free reserved slot, and notes that "the special-block sha changes, which invalidates existing tokenizer builds and packed corpora." That is true, and much more expensive than it sounds. Follow the chain:

special.token_list()  changes
  → vocab.special_tokens_sha()  changes                      (vocab.py:230)
  → vocab.matches() returns False for every built vocabulary (vocab.py:193)
  → the tokenizer is re-learned
  → vocab.file_fingerprint() changes
  → the corpus key changes                                   (pack.py, "keyed on the vocabulary")
  → every packed corpus is re-packed from raw text

On a FineWeb-scale corpus that is hours of BPE training and packing, triggered by a one-line edit, to gain a token that is only ever a placeholder.

Do this instead, for free. token_list() already emits <|reserved_41|>…<|reserved_63|>, and every vocabulary ever built in this repo has already trained them as protected single tokens. Alias one: 
# special.py
IMAGE_SLOT = "<|reserved_41|>"   # the image placeholder, occupying a reserved
                                 # slot by name so `token_list()` is unchanged
                                 # and no vocabulary or corpus is invalidated.
The sha does not move, nothing rebuilds, and the marker can be promoted to a real spelling later at exactly the moment a rebuild is happening anyway. The reserved block was designed for precisely this and the report used it for the id but paid for it anyway.

The recommendation, in three stages

Stage 0 — generate shapes locally. No download. Thirty lines of Pillow: coloured circles/squares/triangles on a plain field, with templated captions ("a red circle above a blue square"). This is the one I would actually start with, and it is not a toy step — it is the only configuration where a from-scratch 6M-parameter encoder can genuinely solve the task, so it gives an unambiguous pass/fail on whether the plumbing works before a single gigabyte is fetched. Captions land at 10–20 tokens, which fits the current 512 window with room to spare.

Stage 1 — jxie/flickr8k for captioning. 40,000 image–caption pairs from 8,000 images, 1.1 GB, images embedded as bytes so there is nothing to crawl. Captions average ~12 tokens. It converts to this repo's SFT JSONL ({"turns":[{"role","text"}]}) with a trivial script, one row per caption. Check the Flickr8k academic-use terms before anything leaves the machine — the HF metadata states no license.

Stage 2 — the_cauldron / clevr for the real evaluation. Two reasons it is the pick. First, its schema is already a user/assistant conversation list, so it maps onto sft.py's format almost without conversion. Second and more important: CLEVR asks compositional questions about counting, attributes and spatial relations over synthetic rendered scenes. The visual domain is closed enough for a small encoder to learn, and — unlike captioning — a model that ignores the pixels cannot fake it.

The experiment neither report proposes, and the one that decides whether any of this worked. At 30M parameters on short captions, the model will learn the caption prior — "a man in a red shirt is …" — and produce fluent, plausible, image-independent output. Loss will fall. Samples will look like it sees. It will not.

So run a text-only control: the identical SFT, with the image tensors zeroed. If the two runs converge to the same loss, the vision stack contributed nothing and the whole feature is decoration. This costs one extra run and is the only honest evidence available. It also fits this repo's existing habit — strip_thinking exists precisely so a control can be built against the same conversations, and test_dataflow_trace.py exists precisely to make behavioural claims falsifiable.

Dependencies

huggingface_hub==1.27.0 and pyarrow==25.0.0 are already in requirements.txt, pulled in by tokenizers — so fetching parquet shards needs no new dependency. Against the report's recommendation, I would take Pillow alone, not torchvision: HF's Image feature stores encoded bytes so Pillow is required regardless, resize-and-normalize is ~15 lines, and torchvision pins hard against a specific torch build for two functions you would write anyway. One new line in requirements.txt, not a framework.

5. Bottom line

The report is worth keeping. Its architectural instinct is right, its read of the trunk is accurate, and its central observation — that this codebase's reserved token slots, existing mask machinery, causal attention and concatenating KV cache leave it unusually ready for a vision path — survives review. The decoder really is untouched.

But do not build from its plan as written. Three concrete corrections: swap concat-at-front for masked-scatter into placeholder positions (which repairs the loss, the RoPE slice and the context guard all at once); alias a reserved marker instead of editing SPECIAL_TOKENS (which avoids re-packing every corpus); and budget the data and batching path honestly, because train/plan.py has no concept of an example and that — not vision.py — is the work. Realistic engine-side cost is 800–1,300 lines, not 350–550, before the Rust and frontend seams.

On data: shapes → flickr8k → CLEVR, with a zeroed-image control run at every stage. The context window has to reach 1024 before an image and a conversation coexist, and on that point the report is exactly right that this is a bigger-context project wearing small-code clothes.
